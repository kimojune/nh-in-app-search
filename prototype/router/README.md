# 크로스 앱 라우터 — 실행 가능한 구현

- 최종 수정일: 2026-08-24
- 문서 유형: 계속 갱신
- 상태: 콘솔·클라이언트·앱 시뮬레이터 동작 확인 완료 / 사용자 효과는 미검증

그룹사가 **어느 업무를 어느 채널이 담당하는가**를 정의·승인·발행하고, 계열사 앱이 그 기준을 받아 검색 결과에 안내를 노출한다. 각 앱의 검색 성능을 개선하는 도구가 아니다.

## 실행

서버 없이 파일을 직접 열면 된다. 두 파일을 **탭 두 개로** 열어야 연동이 보인다.

```text
console.html    라우터 관리 콘솔 — 기준 등록·승인·발행
bank-app.html   계열사 앱 시뮬레이터 — 검색·동기화·계측
```

두 페이지는 같은 폴더(같은 origin)의 브라우저 저장소를 공유하므로 실제로 데이터가 오간다.

## 구조

```text
[계열사 담당자]      [라우터 콘솔]           [발행 스냅샷]          [계열사 앱]
상품·업무 데이터  →  자동 매핑           →  routing-index.json →  routing-client.js
내보내기(CSV)        역할·다음 행동만 수기     version + etag        sync()  하루 1회
                     정규화·표현 확장         index / functions     lookup() 검색마다
                     미노출 지정              (승인된 것만)          네트워크 0
                     중앙 승인 후 발행
```

핵심은 **지능을 중앙에 두고 말단은 사전 조회만 하게 하는 것**이다. 앱은 동의어 판단도, 담당 채널 판단도, 어느 앱에서 안내를 숨길지도 결정하지 않는다. 세 가지 모두 라우터가 발행 시점에 끝내고 스냅샷에 담아 보낸다.

이 설계를 택한 이유는 조직 구조에 있다. NH콕뱅크(상호금융)와 올원뱅크·스마트뱅킹(농협은행)은 감독 체계가 다른 별도 법인이다([`docs/NH앱4개_카드검색_as-is결과.md`](../../docs/NH앱4개_카드검색_as-is결과.md) 「NH 앱 분리의 조직적 배경」). 도입에 요구되는 작업량이 크면 채택되지 않는다.

## 등록 방식 — 계열사는 이미 가진 데이터를 올린다

담당자가 폼을 손으로 채우는 대신 **계열사 시스템에서 내보낸 상품·업무 데이터를 그대로 올린다.** 콘솔이 컬럼을 자동 인식해 매핑하고, 회사 데이터에 없는 값만 담당자가 채운다.

| 값 | 어디서 오는가 |
|---|---|
| 기능 · 업무명 | 올린 데이터 — 업무구분·카테고리 컬럼 |
| 사용자 표현 | 올린 데이터 — 상품명 + 별칭 컬럼. 쉼표로 여러 개 |
| 담당 채널 | 올린 데이터 — 담당앱 컬럼. 이름으로 채널 id를 매칭 |
| 등록 부서 | 올린 데이터 — 담당부서 컬럼 |
| **채널 역할** (완료·경유·안내) | **담당자가 채움** — 회사 데이터에 없는 개념 |
| **다음 행동** | **담당자가 채움** — 회사 데이터에 없는 개념 |

손으로 채우는 칸은 **두 개뿐**이고, 미리보기 표에서 자동으로 채워진 칸과 색으로 구분된다. 기본값을 정해 일괄 적용한 뒤 필요한 행만 고치면 된다.

### 계열사마다 양식이 다르다

계열사는 시스템이 서로 달라 내보내는 파일 양식도 다르다. "우리 양식에 맞춰 다시 만들어 오라"고 요구하면 도입되지 않으므로, **콘솔이 그 차이를 흡수한다.** `samples/`에 실제로 다른 네 가지 양식을 두었다.

| 파일 | 앱 | 구분자 | 특징 | 자동 인식 |
|---|---|---|---|---|
| `01_카드사업부_상품마스터.csv` | NH Pay | 쉼표 | 별칭 한 컬럼, 따옴표 안에 쉼표 | 성공 |
| `02_은행채널부_메뉴트리.csv` | NH올원뱅크 | 쉼표 | **별칭 컬럼 없음** — 표현이 메뉴명 하나 | 성공 |
| `03_상호금융부_업무목록.csv` | NH콕뱅크 | **파이프** | 별칭은 세미콜론, 담당앱이 `콕뱅크` 축약 | 성공 |
| `04_디지털전략부_통합채널.tsv` | NH스마트뱅킹 | **탭** | 컬럼명이 `svc_nm`·`kwd_1` 영문 약어 | **실패 → 수동 매핑** |

4번은 의도적으로 자동 추천이 실패하게 두었다. 머리글이 영문 약어라 이름으로 추정할 수 없고, 이때 매핑 UI가 필요해진다. 컬럼만 드롭다운으로 지정하면 값은 정상 인식된다.

콘솔이 흡수하는 차이는 이렇다.

```text
구분자     쉼표 · 탭 · 파이프 · 세미콜론을 첫 줄 빈도로 자동 감지 (수동 지정도 가능)
컬럼명     한국어 이름 체계를 추정. 실패하면 드롭다운으로 직접 지정
표현 컬럼   여러 컬럼을 함께 고를 수 있다 (상품명 + 별칭, kwd_1 + kwd_2)
값 안 구분  쉼표 · 세미콜론 · 파이프로 나뉜 별칭을 자동 분리
채널 표기   `콕뱅크` · `NH페이` 같은 축약·변형을 별칭 표로 해석
```

샘플 한 줄을 보면

```csv
상품코드,상품명,별칭,담당앱,담당부서,업무구분
CARD-2041,K-패스카드,"K-패스,케이패스,경기패스카드,교통비 환급 카드",NH Pay,카드사업부,교통비 환급 카드 신청
```

여기서 사용자 표현 5개가 만들어진다. 상품명 컬럼과 별칭 컬럼을 함께 고르기 때문이다.

```text
K-패스카드 · K-패스 · 케이패스 · 경기패스카드 · 교통비 환급 카드
```

발행 시 이 표현들이 정규화되어 인덱스 키가 된다. 앱은 어떤 표현이 같은 업무를 가리키는지 알 필요가 없다.

실제 서비스에서는 파일 업로드 자리에 계열사 시스템과의 배치 연동이나 API가 온다. 목록의 `출처` 열이 그 형태(`배치 연동`)를 가리킨다.

콘솔 드롭다운의 샘플은 `samples/` 파일과 **같은 내용의 사본**이다. 한쪽을 고치면 다른 쪽도 고쳐야 하며, 자동 검사가 두 내용이 일치하는지 확인한다.

## 반대 방향 — 로그가 등록할 표현을 알려준다

여기까지는 계열사가 데이터를 **밀어 넣는** 방향이었다. 반대 방향도 된다. 각 앱의 **검색 결과 0건 로그**를 올리면 라우터가 어떤 표현을 등록해야 하는지 역으로 뽑아낸다. 담당자가 무엇을 빠뜨렸는지 기억해낼 필요가 없다.

`samples/05_검색로그_0건쿼리.csv`가 그 입력이다.

```csv
집계일,앱,검색어,검색수,결과수
2026-08-17,NH올원뱅크,케이패스카드,412,0
2026-08-17,NH콕뱅크,k패스,196,0
```

콘솔의 `로그로 후보 찾기` 탭이 각 쿼리를 세 갈래로 가른다.

| 판정 | 뜻 | 조치 |
|---|---|---|
| **미등록** | 기준에 없는 표현 | 붙일 기능을 골라 표현으로 추가 |
| **이미 등록됨** | 기준에는 있는데 0건이 나옴 | 그 앱이 아직 스냅샷을 받지 않았을 수 있음 |
| **등록됨 · 미승인** | 등록은 됐으나 발행 전 | 승인하고 발행하면 해결 |

미등록 표현에는 **붙일 기능을 자동으로 추천**한다. 정확 일치·포함 관계·앞부분 일치·글자 겹침을 섞은 단순 점수이며, 검색 엔진 수준의 매칭이 아니다. 애매하면 사람이 드롭다운으로 고른다.

샘플 로그를 넣고 카드사업부·디지털전략부 데이터가 등록된 상태에서 돌린 실제 결과는 이렇다.

```text
미등록   케이패스카드    412회   → 추천: 교통비 환급 카드 신청
미등록   경기패스        288회   → 추천: 교통비 환급 카드 신청
등록됨   k패스           196회   → 앱 미동기화 의심
미등록   교통카드 신청    151회   → 추천 없음, 사람이 선택
미등록   올바른이음      143회   → 추천 없음, 사람이 선택
미등록   출자금 배당금     97회   → 추천: 조합원 배당 조회
미등록   통장사본 발급     88회   → 추천: 증명서 발급
미등록   자동이체 끊기     64회   → 추천: 자동이체 해지

총 검색 1,439회 · 미등록 7건 · 미등록이 차지하는 검색 비중 86%
```

**7건만 등록하면 0건 검색의 86%가 담당 채널 안내를 받는다.** 그중 5건은 추천이 자동으로 붙고 사람이 고르는 건 2건뿐이다.

승인된 기준에 표현을 추가하면 상태가 **`검토 중`으로 되돌아간다.** 승인된 내용을 고쳤으니 다시 승인을 받아야 하기 때문이다. 로그에서 뽑은 후보라고 해서 승인 절차를 건너뛰지 않는다.

## 앱이 심는 코드 전부

```js
const client = new RoutingClient("allone", transports.http("/routing-index.json"));

await client.sync();                    // 하루 1회. 검색 경로에서는 부르지 않는다
const hit = client.lookup(query);       // 검색마다. 네트워크 0, 해시 조회 1회
if (hit) renderGuide(hit.name, hit.channels, hit.next);
```

전체 구현은 [`routing-client.js`](./routing-client.js)에 있고 핵심 로직은 `sync()`와 `lookup()` 두 함수다.

## 스냅샷 스키마

```json
{
  "version": 2,
  "publishedAt": "2026-08-24T...",
  "tenant": "nh-financial",
  "etag": "v2-3f9a1c",
  "index":     { "k패스카드": "f-001", "케이패스": "f-001", "교통비환급카드": "f-001" },
  "functions": {
    "f-001": {
      "name": "교통비 환급 카드 신청",
      "next": "카드 목록에서 K-패스카드를 찾아 신청",
      "suppressIn": ["nhpay"],
      "channels": [
        { "id": "nhpay",   "name": "NH Pay",             "role": "완료" },
        { "id": "cardweb", "name": "NH농협카드 모바일웹", "role": "완료" },
        { "id": "allone",  "name": "NH올원뱅크",          "role": "안내" }
      ]
    }
  }
}
```

- `index`는 **정규화된 키 → 기능 id** 사전이다. 정규화(공백·하이픈·언더스코어·가운뎃점 제거, 소문자화)는 발행 시점에 라우터가 적용한다.
- `suppressIn`은 안내를 노출하지 않을 접점이다. 담당 채널 본인에게 중복 안내를 띄우지 않기 위한 것이며, 이 판단도 중앙이 한다.
- 필드는 [`docs/B축_MVP_설계.md`](../../docs/B축_MVP_설계.md) 「핵심 데이터 구조」의 6개 필드를 따른다. `상태`는 콘솔 내부 값이고 승인된 것만 스냅샷에 나간다.

## 앱이 가벼운 이유

| 축 | 설계 | 측정·근거 |
|---|---|---|
| 네트워크 | 하루 1회 조건부 GET(ETag). 검색 시 호출 없음 | 변경 없으면 **304 · 본문 0 B** |
| 연산 | 정규화 키를 라우터가 미리 펼쳐 내려줌 | **해시 조회 1회**. 매칭 판단 없음 |
| 코드 | SDK·라이브러리 없이 함수 2개 | 호출부 **4줄**, 클라이언트 핵심 로직 약 40줄 |
| 배포 주기 | 기준 변경이 스냅샷 교체로 끝남 | **앱 스토어 배포 불필요** |

측정한 스냅샷 크기 (기능 1건 + 표현 키 4개 기준)

```text
기능 1건        549 B
기능 500건 추정  약 268 KB (gzip 전)
```

## 프로덕션 대응표

이 구현은 서버가 없다. 실제 서비스에서 무엇이 바뀌는지 명시한다.

| 이 데모 | 실제 서비스 |
|---|---|
| 콘솔이 브라우저 저장소에 스냅샷을 쓴다 | 콘솔이 오브젝트 스토리지에 올리고 CDN이 배포 |
| `transports.local()` | `transports.http()` — 코드는 이미 들어 있다 |
| ETag를 문자열 비교로 재현 | HTTP `If-None-Match` / `304 Not Modified` |
| 앱 캐시 = `localStorage` | 앱 내부 저장소 또는 파일 캐시 |
| 승인 = 버튼 클릭 | 권한 분리된 승인 워크플로 + 감사 로그 |
| 부서 = 입력 필드 | 조직 계정·권한 체계 |

`sync()`와 `lookup()`의 로직은 두 경우가 동일하고 바뀌는 것은 전송 계층뿐이다.

## 검증

동작 확인은 아래 순서로 한다. `prototype/router/`에서 두 파일을 탭 두 개로 연다.

1. 앱 탭에서 `k패스카드` 검색 → 안내 없음, 계측에 `캐시 버전: 없음`
1-1. 콘솔 `로그로 후보 찾기` 탭 → `샘플 로그 불러오기` → 미등록 7건과 추천 확인 → `표현 추가` 몇 건
2. 콘솔 탭에서 `계열사 샘플 불러오기` 드롭다운으로 네 양식을 차례로 불러온다 → 미리보기에서 자동·수기 칸 확인 → `기본값 채우기` → `등록 요청` → `일괄 검토 요청` → `일괄 승인` → `승인된 기준 발행`
3. 앱 탭에서 `동기화` → 로그에 `200 OK · 수신 N B · v1` → 같은 검색어에 안내 노출
4. 앱 탭에서 `동기화` 재실행 → `304 Not Modified · 수신 0 B`
5. 앱 선택을 `NH Pay`로 바꾸고 같은 검색 → 안내 대신 미노출 사유 표시
6. 콘솔에서 `NH농협카드 모바일웹`을 `미사용`으로 바꾸고 재발행 → 앱에서 동기화 → 그 줄이 사라짐
7. 앱 탭에서 `캐시 비우기` → 검색은 정상, 안내만 사라짐
8. 앱 탭에서 `스냅샷 손상시키기` → 같은 결과(예외 없음)

발행·동기화·조회·폴백을 자동 검사로도 확인했다. 24개 항목 전부 통과했으며, 검사 대상은 화면이 아니라 `routing-client.js` 실제 코드다.

## 고지와 한계

- 이 화면들은 기획 검증용 **목업**이다. 실제 NH농협 서비스가 아니며 NH농협과 무관하다. 실제 계좌·카드 신청은 일어나지 않고 개인정보를 수집하지 않는다.
- as-is 검색 결과는 2026-08-18~20에 실제 앱에서 검색해 기록한 값이다. 출처는 각 파일 주석과 [`docs/NH앱4개_카드검색_as-is결과.md`](../../docs/NH앱4개_카드검색_as-is결과.md)에 있다.
- **안내가 사용자를 실제로 돕는지는 검증하지 않았다.** After 사용성 테스트는 이번 범위에서 제외했다. 제시할 수 있는 수치는 커버리지와 도입 비용이며 사용자 효과가 아니다.
- as-is 데이터는 본인이 직접 검색한 n=1 기록이고, 비교 검색어 확인도 스마트뱅킹 1건뿐이다.
- 서버가 없어 여러 기기·여러 사람 간 공유는 되지 않는다.
