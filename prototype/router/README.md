# 크로스 앱 라우터 — 실행 가능한 구현

- 최종 수정일: 2026-08-25
- 문서 유형: 종료 시점 스냅샷 — 이후 갱신하지 않는다
- 상태: 콘솔·클라이언트·앱 시뮬레이터 동작 확인 완료 / 사용자 효과는 미검증

그룹사가 **어느 업무를 어느 채널이 담당하는가**를 정의·승인·발행하고, 계열사 앱이 그 기준을 받아 검색 결과에 안내를 노출한다. 각 앱의 검색 성능을 개선하는 도구가 아니다.

## 실행

서버 없이 파일을 직접 열면 된다. 두 파일을 **탭 두 개로** 열어야 연동이 보인다.

```text
console.html      라우터 관리 콘솔 — 기준 등록·승인·발행
bank-app.html     계열사 앱 시뮬레이터 — 검색·동기화·계측
routing-client.js 앱이 라우터에서 기준을 받아 조회하는 부분
app-themes.js     받은 데이터를 그 앱의 디자인으로 그리는 부분
```

두 페이지는 같은 폴더(같은 origin)의 브라우저 저장소를 공유하므로 실제로 데이터가 오간다.

### 발표 모드

`bank-app.html` 헤더 오른쪽의 `발표 모드` 버튼을 누르면 화면이 시연용으로 바뀐다.

| | 평소 | 발표 모드 |
|---|---|---|
| 설명 문단·캡션·코드 패널 | 보임 | 접힘 |
| 폰 | 왼쪽 340px | **가운데 · 1.3배** |
| 측정값 | 5줄 | 핵심 3줄 + 동기화 로그 |
| 목업 고지 | 3줄 | 1줄 (없애지 않는다) |
| 안내 미노출 쪽지 | 폰 안에 보임 | 감춤 |
| 네 앱 비교 패널 | 켠 상태 유지 | 접힘 |

안내가 안 뜬 이유를 밝히는 쪽지(`이 앱이 담당 채널 본인입니다` 등)는 **관찰자용 설명이지 사용자 화면이 아니다.** 실제 사용자는 그런 문장을 보지 않는다. 그래서 발표 모드에서는 감춰 폰이 사용자가 보는 화면 그대로가 되게 하고, 평소에는 남겨 둔다 — 혼자 열어보는 사람에게는 그것이 왜 아무것도 안 떴는지 알 유일한 단서다. 감춰도 안 뜬 사실 자체는 오른쪽 동기화 로그의 `lookup` 기록에 남는다.

헤더의 닫기 `×`는 실제로 동작한다 — 검색어와 결과를 지우고 첫 화면으로 돌아간다. 스냅샷과 동기화 상태는 그대로 두므로, 앱을 초기화하는 `캐시 비우기`와는 다르다. 폰 안에서 아직 동작하지 않는 것은 탭과 추천검색어뿐이다.

### 네 앱 비교

헤더의 `네 앱 비교` 버튼을 누르면 **같은 안내 데이터를 네 앱이 각자의 디자인으로 그린 결과**가 나란히 나온다. 검색을 하면 그 조회 결과로 다시 그리고, 아직 조회한 게 없으면 예시 데이터로 그린다 — 화면에 어느 쪽인지 밝힌다. 선택은 저장되므로 새로고침해도 유지된다.

발표 모드에서는 접힌다. 시연은 한 앱에서 0건 → 안내가 붙는 흐름을 보여주는 자리이고, 비교는 그 뒤 설계 판단을 설명할 때 쓰는 자리다.

설명을 **지우는 게 아니라 감춘다.** 발표에서는 발표자가 말로 설명하지만, 제출물을 혼자 열어보는 사람에게는 그 설명이 유일한 안내이기 때문이다.

선택은 브라우저에 저장되므로 발표 중 새로고침해도 설명이 다시 나오지 않는다. CSS와 클래스 토글만 쓰고 조회·동기화 로직은 건드리지 않는다.

## 구조

```text
[계열사 담당자]      [라우터 콘솔]           [발행 스냅샷]          [계열사 앱]
상품·업무 데이터  →  자동 매핑           →  routing-index.json →  routing-client.js
내보내기(CSV)        역할·다음 행동만 수기     version + etag        sync()  하루 1회
                     정규화·표현 확장         index / functions     lookup() 검색마다
                     미노출 지정              (승인된 것만)          네트워크 0
                     중앙 승인 후 발행                                     ↓ 데이터만
                                                                    app-themes.js
                                                                    그 앱의 컴포넌트로
                                                                    화면을 그린다
```

핵심은 **지능을 중앙에 두고 말단은 사전 조회만 하게 하는 것**이다. 앱은 동의어 판단도, 담당 채널 판단도, 어느 앱에서 안내를 숨길지도 결정하지 않는다. 세 가지 모두 라우터가 발행 시점에 끝내고 스냅샷에 담아 보낸다.

이 설계를 택한 이유는 조직 구조에 있다. NH콕뱅크(상호금융)와 올원뱅크·스마트뱅킹(농협은행)은 감독 체계가 다른 별도 법인이다([`docs/NH앱4개_카드검색_as-is결과.md`](../../docs/NH앱4개_카드검색_as-is결과.md) 「NH 앱 분리의 조직적 배경」). 도입에 요구되는 작업량이 크면 채택되지 않는다.

## 화면은 앱이 그린다 — 앱마다 디자인이 다르기 때문에

라우터가 앱에 주는 것은 데이터뿐이다.

```json
{ "name": "교통비 환급 카드 신청",
  "next": "카드 목록에서 K-패스카드를 찾아 신청",
  "channels": [{ "id": "nhpay", "name": "NH Pay", "role": "완료" }] }
```

**안내 카드의 마크업과 스타일은 라우터가 내려보내지 않는다.** 각 앱이 자기 컴포넌트로 그린다. `app-themes.js`가 그 부분이고, 네 앱의 렌더러가 같은 함수 이름으로 서로 다른 화면을 만든다.

```js
renderers[appId].guideCard(hit)      // 안내 카드
                .channelRow(ch)      // 채널 한 줄
                .roleBadge(role)     // 완료 · 경유 · 안내
                .sectionHeader(s)    // "메뉴 39건" / "메뉴 (총 15건)" / "카드 2"
                .resultRow(html)     // 결과 한 줄
                .emptyState(sec)     // 0건 화면
```

이렇게 나눈 이유는 실측에 있다. 네 앱은 **디자인 언어가 서로 다르다.**

| | 강조색 | 헤더 | 검색창 | 결과 강조 |
|---|---|---|---|---|
| NH올원뱅크 | `#18983B` 초록 | 가운데 정렬 + ✕ | 회색 테두리 박스 | 마지막 조각 초록 + 밑줄 |
| NH콕뱅크 | `#0296A2` **청록** | 왼쪽 + ✕ | 청록 알약형 | — |
| NH스마트뱅킹 | `#229142` 초록 | 왼쪽 + ✕ | 초록 테두리 박스 | 매칭 토큰만 초록 |
| NH Pay | `#313E60` **네이비** | 뒤로가기 `<` | 밑줄형 | 매칭 토큰 파랑 |

값은 as-is 캡처에서 픽셀로 뽑았다. 측정 방법과 한계, 접근성 대비 검증은 [`docs/디자인_기준.md`](../../docs/디자인_기준.md)에 있다.

**실측한 강조색 중 셋이 본문 크기 텍스트에서 WCAG AA 대비(4.5:1)에 미달한다.** 라우터가 안내 카드 UI를 직접 내려보냈다면 네 앱 각각의 디자인 시스템과 접근성 기준을 라우터가 떠안게 된다. 데이터만 주고 화면을 앱에 맡긴 판단에는 이 근거가 있다.

앱이 정하는 것은 안내 카드만이 아니다. 안드로이드는 **상태바와 하단 내비게이션 바의 색도 앱이 지정**하는데, 실측에서 여기도 갈렸다.

| | 상태바 | 하단 내비게이션 |
|---|---|---|
| NH올원뱅크 · NH콕뱅크 | 흰색 | 흰색 |
| NH스마트뱅킹 | 흰색 | `#343434` |
| NH Pay | `#303030` | `#1D1D1D` |

폰은 **CSS로 그린 안드로이드 디바이스 프레임**에 들어 있다. 실측이 삼성/안드로이드이므로 아이폰 프레임을 쓰지 않는다 — 쓰면 리서치와 화면이 어긋난다. 베젤·라운드·그림자와 하단 세 버튼(최근·홈·뒤로)까지 도형으로 그렸고, 목업 도구나 기기 사진은 쓰지 않는다.

로고·마스코트 같은 상표 요소는 재현하지 않는다. 색·타이포·레이아웃·컴포넌트 형태까지만 따르고, 콕뱅크 0건 화면의 캐릭터 자리는 중립 도형으로 두고 캡션으로 사실을 밝힌다.

## 등록 방식 — 계열사는 이미 가진 데이터를 올린다

담당자가 폼을 손으로 채우는 대신 **계열사 시스템에서 내보낸 상품·업무 데이터를 그대로 올린다.** 콘솔이 컬럼을 자동 인식해 매핑하고, 회사 데이터에 없는 값만 담당자가 채운다.

| 값 | 어디서 오는가 |
|---|---|
| 기능 · 업무명 | 올린 데이터 — 업무구분·카테고리 컬럼 |
| 사용자 표현 | 올린 데이터 — 상품명 + 별칭 컬럼. 쉼표로 여러 개 |
| 담당 채널 | 올린 데이터 — 담당앱 컬럼. 이름으로 채널 id를 매칭 |
| 등록 부서 | 올린 데이터 — 담당부서 컬럼 |
| **채널 역할** (완료·경유·안내) | **담당자가 채움** — 회사 데이터에 없는 개념 |
| **다음 행동** | **담당자가 채움** — 회사 데이터에 없는 개념 |

손으로 채우는 칸은 **두 개뿐**이고, 미리보기 표에서 자동으로 채워진 칸과 색으로 구분된다. 기본값을 정해 일괄 적용한 뒤 필요한 행만 고치면 된다.

### 계열사마다 양식이 다르다

계열사는 시스템이 서로 달라 내보내는 파일 양식도 다르다. "우리 양식에 맞춰 다시 만들어 오라"고 요구하면 도입되지 않으므로, **콘솔이 그 차이를 흡수한다.** `samples/`에 실제로 다른 네 가지 양식을 두었다.

| 파일 | 앱 | 구분자 | 특징 | 자동 인식 |
|---|---|---|---|---|
| `01_카드사업부_상품마스터.csv` | NH Pay | 쉼표 | 별칭 한 컬럼, 따옴표 안에 쉼표 | 성공 |
| `02_은행채널부_메뉴트리.csv` | NH올원뱅크 | 쉼표 | **별칭 컬럼 없음** — 표현이 메뉴명 하나 | 성공 |
| `03_상호금융부_업무목록.csv` | NH콕뱅크 | **파이프** | 별칭은 세미콜론, 담당앱이 `콕뱅크` 축약 | 성공 |
| `04_디지털전략부_통합채널.tsv` | NH스마트뱅킹 | **탭** | 컬럼명이 `svc_nm`·`kwd_1` 영문 약어 | **실패 → 수동 매핑** |

4번은 의도적으로 자동 추천이 실패하게 두었다. 머리글이 영문 약어라 이름으로 추정할 수 없고, 이때 매핑 UI가 필요해진다. 컬럼만 드롭다운으로 지정하면 값은 정상 인식된다.

콘솔이 흡수하는 차이는 이렇다.

```text
구분자     쉼표 · 탭 · 파이프 · 세미콜론을 첫 줄 빈도로 자동 감지 (수동 지정도 가능)
컬럼명     한국어 이름 체계를 추정. 실패하면 드롭다운으로 직접 지정
표현 컬럼   여러 컬럼을 함께 고를 수 있다 (상품명 + 별칭, kwd_1 + kwd_2)
값 안 구분  쉼표 · 세미콜론 · 파이프로 나뉜 별칭을 자동 분리
채널 표기   `콕뱅크` · `NH페이` 같은 축약·변형을 별칭 표로 해석
```

샘플 한 줄을 보면

```csv
상품코드,상품명,별칭,담당앱,담당부서,업무구분
CARD-2041,K-패스카드,"K-패스,케이패스,경기패스카드,교통비 환급 카드",NH Pay,카드사업부,교통비 환급 카드 신청
```

여기서 사용자 표현 5개가 만들어진다. 상품명 컬럼과 별칭 컬럼을 함께 고르기 때문이다.

```text
K-패스카드 · K-패스 · 케이패스 · 경기패스카드 · 교통비 환급 카드
```

발행 시 이 표현들이 정규화되어 인덱스 키가 된다. 앱은 어떤 표현이 같은 업무를 가리키는지 알 필요가 없다.

실제 서비스에서는 파일 업로드 자리에 계열사 시스템과의 배치 연동이나 API가 온다. 목록의 `출처` 열이 그 형태(`배치 연동`)를 가리킨다.

콘솔 드롭다운의 샘플은 `samples/` 파일과 **같은 내용의 사본**이다. 한쪽을 고치면 다른 쪽도 고쳐야 하며, 자동 검사가 두 내용이 일치하는지 확인한다.

## 반대 방향 — 로그가 등록할 표현을 알려준다

여기까지는 계열사가 데이터를 **밀어 넣는** 방향이었다. 반대 방향도 된다. 각 앱의 **검색 결과 0건 로그**를 올리면 라우터가 어떤 표현을 등록해야 하는지 역으로 뽑아낸다. 담당자가 무엇을 빠뜨렸는지 기억해낼 필요가 없다.

> **이 로그는 이 데모의 앱이 만든 것이 아니다.** `bank-app.html`은 0건 검색을 기록하지 않는다. 여기서 쓰는 것은 미리 만들어 둔 `samples/05_검색로그_0건쿼리.csv`이고, 그 안의 검색수는 실측이 아니라 예시값이다. 로그 형식에 `집계일`과 `검색수`가 있는 데서 보이듯 이것은 하루치를 모아 세는 작업이라, 실제 서비스에서도 앱 클라이언트가 아니라 각 사의 검색 로그 분석에서 나온다. 앱에 검색어 수집을 넣으면 `앱은 조회만 한다`는 설계와도, 사용자 검색어를 다른 법인으로 보내지 않는다는 판단과도 어긋난다.

`samples/05_검색로그_0건쿼리.csv`가 그 입력이다.

```csv
집계일,앱,검색어,검색수,결과수
2026-08-17,NH올원뱅크,케이패스카드,412,0
2026-08-17,NH콕뱅크,k패스,196,0
```

콘솔의 `로그로 후보 찾기` 탭이 각 쿼리를 세 갈래로 가른다.

| 판정 | 뜻 | 조치 |
|---|---|---|
| **미등록** | 기준에 없는 표현 | 붙일 기능을 골라 표현으로 추가 |
| **이미 등록됨** | 기준에는 있는데 0건이 나옴 | 그 앱이 아직 스냅샷을 받지 않았을 수 있음 |
| **등록됨 · 미승인** | 등록은 됐으나 발행 전 | 승인하고 발행하면 해결 |

미등록 표현에는 **붙일 기능을 자동으로 추천**한다. 정확 일치·포함 관계·앞부분 일치·글자 겹침을 섞은 단순 점수이며, 검색 엔진 수준의 매칭이 아니다. 애매하면 사람이 드롭다운으로 고른다.

샘플 로그를 넣고 카드사업부·디지털전략부 데이터가 등록된 상태에서 돌린 실제 결과는 이렇다.

```text
미등록   케이패스카드    412회   → 추천: 교통비 환급 카드 신청
미등록   경기패스        288회   → 추천: 교통비 환급 카드 신청
등록됨   k패스           196회   → 앱 미동기화 의심
미등록   교통카드 신청    151회   → 추천 없음, 사람이 선택
미등록   올바른이음      143회   → 추천 없음, 사람이 선택
미등록   출자금 배당금     97회   → 추천: 조합원 배당 조회
미등록   통장사본 발급     88회   → 추천: 증명서 발급
미등록   자동이체 끊기     64회   → 추천: 자동이체 해지

총 검색 1,439회 · 미등록 7건 · 미등록이 차지하는 검색 비중 86%
```

**7건만 등록하면 0건 검색의 86%가 담당 채널 안내를 받는다.** 그중 5건은 추천이 자동으로 붙고 사람이 고르는 건 2건뿐이다.

`86%`는 **위 샘플 로그를 기준으로 계산한 값이지 실제 사용자 검색을 측정한 값이 아니다.** 콘솔이 실제로 계산해 낸 숫자이므로 계산 자체는 재현되지만, 입력이 예시값이므로 실제 서비스에서 같은 비율이 나온다는 근거는 없다.

## 발행 전에 걸리는 확인 관문

승인되지 않은 기준은 발행되지 않는다. 그래서 승인을 건너뛰면 **빈 기준이 정상적으로 발행되고**, 앱은 동기화에 성공(200 OK)하고도 아무 안내를 띄우지 못한다. 등록·발행·동기화를 다 했는데 검색이 안 되는 상태가 되고, 화면 어디에도 이유가 없다.

두 자리를 막았다.

| 언제 | 무엇을 하는가 |
|---|---|
| 승인된 기준이 0건인데 발행을 누름 | 발행을 멈추고, 빈 기준이 나가면 어떻게 되는지 알린다 |
| 이전에 발행된 기준이 이번에 빠짐 | 빠지는 기준의 이름을 나열하고 계속할지 묻는다 |
| 내용이 지난 발행과 똑같음 | 발행하지 않고 `v{N} 그대로입니다`라고 알린다 |
| 발행된 기준을 지우려 함 | 앱에 나가 있다는 것과 발행해야 반영된다는 것을 알리고 되묻는다 |

두 번째는 **승인된 기준에 표현을 추가하면 상태가 `검토 중`으로 되돌아가기 때문**에 생긴다. 재승인 없이 발행하면 그 기준이 스냅샷에서 통째로 빠져서, 지금까지 되던 안내까지 함께 사라진다.

세 번째는 이 구조의 전제를 지키기 위한 것이다. 발행할 때마다 버전과 `etag`가 올라가면 **앱은 똑같은 내용을 200으로 다시 내려받는다.** 바뀐 게 없을 때 `304 · 수신 0 B`로 끝나는 것이 이 설계가 내세우는 성질이므로, 발행 여부를 내용 해시로 판정한다. `etag`는 `v{버전}-{내용 해시}` 형식이고, 내용이 같으면 버전도 올라가지 않는다.

발행 바에는 `승인 대기 N건`이 항상 떠 있고, 발행 후 문구도 몇 건이 빠졌는지 함께 알린다. 앱 쪽 계측은 스냅샷을 받았는데 표현 키가 `0`이면 경고색으로 바뀐다.

## 기준 삭제

잘못 올린 기준을 지울 방법이 없었다. `전체 초기화`밖에 없었고 그건 승인 상태와 발행 이력까지 다 날린다. 그래서 행마다 `삭제`를 뒀다. **승인된 기준도 지울 수 있다** — 잘못 올린 줄을 되돌리는 유일한 길이다.

**삭제는 지우고 끝나는 동작이 아니다.** 이미 발행된 기준을 지우면 계열사 앱에 나가 있는 안내가 **다음 발행에서** 사라진다. 지우는 순간이 아니라 발행하는 순간에 반영된다. 그래서 지우기 전에 무슨 일이 벌어지는지 계산해 알린다.

| 지우려는 기준 | 확인창이 말하는 것 |
|---|---|
| 발행된 적 없음 | 계열사 앱에는 영향이 없다 |
| 발행돼 있음 | 지금 앱에 나가 있고, `승인된 기준 발행`을 눌러야 앱에서 사라진다 |
| 발행돼 있고 유일한 승인 | 지우면 승인이 0건이 돼 **관문 1이 발행을 막는다.** 앱에 나가 있는 안내를 지우려면 다른 기준을 승인해 함께 발행하거나 앱에서 `캐시 비우기`를 써야 한다 |

마지막 줄이 막다른 길이다. 빈 기준을 발행하지 않는 것은 의도한 설계이므로, 삭제만으로는 앱을 비울 수 없다. 그 사실을 지우기 전에 알린다.

지운 뒤에는 발행 바에 **`발행하면 앱에서 N건이 사라집니다`** 가 계속 뜬다. 발행을 눌러야 알게 되는 것과, 누르기 전에 아는 것은 다르다. 승인이 풀려 빠지는 경우에도 같은 자리에 뜬다.

## 발행 이력과 되돌리기

관문을 세 개 세워도 잘못된 발행은 나갈 수 있다. 나간 뒤에 되돌릴 방법이 필요하다.

발행할 때마다 스냅샷이 이력에 쌓이고, 목록에서 이전 버전을 골라 되돌릴 수 있다. 브라우저 저장소를 쓰므로 **최근 10건까지만** 보관한다.

```text
버전   발행 시각              기능   표현 키   크기      etag          
v4    2026-08-25 14:32:07    5건    18개     1,204 B   v4-3f9a1c   현재
v3    2026-08-25 14:28:51    2건     4개       608 B   v3-8b2e77   [되돌리기]
```

되돌리기에는 규칙이 둘 있다.

**버전을 되감지 않는다.** v3으로 되돌리면 그 내용이 **v5로 새로 나간다.** 과거 번호를 다시 쓰면 지금 무엇이 배포돼 있는지 알 수 없게 되기 때문이며, 실제 배포도 이렇게 한다.

**발행 결과만 되돌린다.** 콘솔의 등록 목록과 승인 상태는 그대로 남는다. 실제 서비스에서도 배포를 되돌리는 것과 원본 데이터를 되돌리는 것은 별개다. 되돌린 뒤 다시 발행하면 되돌린 내용이 아니라 **현재 승인된 내용**이 나간다.

되돌리기 전에 지금 나가 있는 기준 중 무엇이 빠지는지 이름으로 알려주고, 지금과 같은 내용이면 되돌리지 않는다.

`이력 비우기`는 되돌릴 수 있는 이전 발행만 지우고 **지금 배포된 버전 한 줄은 남긴다.** 목록은 비었는데 앱에는 무언가 나가 있는 상태가 더 헷갈리기 때문이다. 등록 목록과 앱에 나가 있는 내용은 건드리지 않으므로, 사라지는 것은 되돌릴 대상뿐이다. 전부 지우려면 `전체 초기화`를 쓴다 — 그쪽은 등록한 규칙까지 함께 지운다.

승인된 기준에 표현을 추가하면 상태가 **`검토 중`으로 되돌아간다.** 승인된 내용을 고쳤으니 다시 승인을 받아야 하기 때문이다. 로그에서 뽑은 후보라고 해서 승인 절차를 건너뛰지 않는다.

## 앱이 심는 코드 전부

```js
const client = new RoutingClient("allone", transports.http("/routing-index.json"));

await client.sync();                    // 하루 1회. 검색 경로에서는 부르지 않는다
const hit = client.lookup(query);       // 검색마다. 네트워크 0, 해시 조회 1회
if (hit) render(AppComponents.guideCard(hit));   // 화면은 이 앱이 그린다
```

라우터에서 받아 조회하는 부분은 [`routing-client.js`](./routing-client.js)이고 핵심 로직은 `sync()`와 `lookup()` 두 함수다. 마지막 줄의 `AppComponents`는 **앱이 이미 갖고 있는 디자인 시스템**을 가리킨다 — 이 데모에서는 [`app-themes.js`](./app-themes.js)가 네 앱 몫을 대신 구현했다. 실제 도입에서는 각 앱의 컴포넌트로 대체되고, 그때 바뀌는 것은 이 한 줄뿐이다.

## 스냅샷 스키마

```json
{
  "version": 2,
  "publishedAt": "2026-08-24T...",
  "tenant": "nh-financial",
  "etag": "v2-3f9a1c",
  "index":     { "k패스카드": "f-001", "케이패스": "f-001", "교통비환급카드": "f-001" },
  "functions": {
    "f-001": {
      "name": "교통비 환급 카드 신청",
      "next": "카드 목록에서 K-패스카드를 찾아 신청",
      "suppressIn": ["nhpay"],
      "channels": [
        { "id": "nhpay",   "name": "NH Pay",             "role": "완료" },
        { "id": "cardweb", "name": "NH농협카드 모바일웹", "role": "완료" },
        { "id": "allone",  "name": "NH올원뱅크",          "role": "안내" }
      ]
    }
  }
}
```

- `index`는 **정규화된 키 → 기능 id** 사전이다. 정규화(공백·하이픈·언더스코어·가운뎃점 제거, 소문자화)는 발행 시점에 라우터가 적용한다.
- `suppressIn`은 안내를 노출하지 않을 접점이다. 담당 채널 본인에게 중복 안내를 띄우지 않기 위한 것이며, 이 판단도 중앙이 한다.
- 필드는 [`docs/B축_MVP_설계.md`](../../docs/B축_MVP_설계.md) 「핵심 데이터 구조」의 6개 필드를 따른다. `상태`는 콘솔 내부 값이고 승인된 것만 스냅샷에 나간다.

## 앱이 가벼운 이유

| 축 | 설계 | 측정·근거 |
|---|---|---|
| 네트워크 | 하루 1회 조건부 GET(ETag). 검색 시 호출 없음 | 변경 없으면 **304 · 본문 0 B** |
| 회복 | 캐시를 못 읽으면 ETag를 버리고 다음 동기화에서 전부 다시 받는다 | 손상 뒤 **동기화 1회로 복구** |
| 이상 입력 | 등록된 표현일 수 없는 길이는 정규화 전에 끊는다 | 1 MB 입력도 **짧은 검색어와 같은 시간** |
| 연산 | 정규화 키를 라우터가 미리 펼쳐 내려줌 | **해시 조회 1회**. 매칭 판단 없음 |
| 크기 내성 | 받은 스냅샷을 한 번만 펼쳐 들고 있는다 | 명부가 커져도 조회 시간이 **그대로** |
| 코드 | SDK·라이브러리 없이 함수 2개 | 호출부 **4줄**, 클라이언트 핵심 로직 약 40줄 |
| 배포 주기 | 기준 변경이 스냅샷 교체로 끝남 | **앱 스토어 배포 불필요** |

측정값 (2026-08-25 재측정, PC 기준. 실제 기기에서는 다를 수 있다)

```text
스냅샷 크기    기능 1건 · 표현 4개          549 B      샘플 데이터 실측
              기능 500건 · 표현 2,000개    약 214 KB   합성 명부
              기능 500건 · 표현 10,000개   약 483 KB   합성 명부
              기능 2,000건 · 표현 40,000개 약 1,958 KB 합성 명부

전송 크기      위는 모두 **압축 전** 크기다. 실제 전송에는 gzip이 걸린다.
              별도 합성 명부(표현·채널·문구를 흩어 생성)로 잰 압축률은 13~16%였고,
              같은 비율을 적용하면 기능 500건은 약 31 KB, 기능 2,000건은 약 340 KB다.
              (2026-08-26 측정. 위 raw 수치와 생성기가 달라 근사값으로 본다)

동기화 요청    조건부 GET 1회 — 요청·304 응답 헤더만 약 600 B. 한 달 약 18 KB

조회 1회       위 어느 크기에서도           0.0002 ms   node tests.mjs 7번 항목
```

**명부 크기가 조회 시간을 바꾸지 않는다**는 것이 이 구조의 핵심이며, 검사 7번이 그걸 확인한다.

조회 비용이 비례하는 것은 명부가 아니라 **검색어 길이**다. 정규화가 글자 수만큼 훑기 때문이다. 계열사 앱의 입력창은 이 코드가 통제할 수 없으므로 `MAX_QUERY = 256`자를 넘는 검색어는 정규화 전에 끊는다. 실제 등록된 표현은 `samples/` 기준 가장 긴 것이 12자(정규화 후 10자)이고 분리자가 낀 경우의 원문/정규화 비율도 최대 1.4배였으므로, 256자는 20배가 넘는 여유다. 그보다 긴 검색어는 등록된 표현과 일치할 수 없어 결과도 달라지지 않는다.

```text
검색어 길이      막기 전      막은 뒤
     40자      0.0005 ms 미만   0.0005 ms 미만
  2,000자        0.0159 ms     0.0005 ms 미만
 50,000자        0.4306 ms     0.0005 ms 미만
1,000,000자     12.6956 ms     0.0005 ms 미만
```

2026-08-25 이전 코드는 검색할 때마다 저장소에서 스냅샷 문자열을 읽어 통째로 다시 펼쳤다. 483 KB 명부에서 검색 1회에 **1.93 ms**가 들었고, 명부가 커질수록 늘어났다. 지금은 받은 뒤 한 번만 펼쳐 들고 있으므로 두 번째 조회부터 **0.0002 ms**다. 저장소가 이 클라이언트 밖에서 바뀌면(다른 탭의 발행, 손상) `refresh()`로 사본을 버리고 다시 읽는다.

## 프로덕션 대응표

이 구현은 서버가 없다. 실제 서비스에서 무엇이 바뀌는지 명시한다.

| 이 데모 | 실제 서비스 |
|---|---|
| 콘솔이 브라우저 저장소에 스냅샷을 쓴다 | 콘솔이 오브젝트 스토리지에 올리고 CDN이 배포 |
| `transports.local()` | `transports.http()` — 코드는 이미 들어 있다 |
| ETag를 문자열 비교로 재현 | HTTP `If-None-Match` / `304 Not Modified` |
| 앱 캐시 = `localStorage` | 앱 내부 저장소 또는 파일 캐시 |
| 승인 = 버튼 클릭 | 권한 분리된 승인 워크플로 + 감사 로그 |
| 삭제 = 즉시 반영, 되돌릴 수 없음 | 삭제 이력과 복구. 누가 언제 무엇을 지웠는지 남는다 |
| 발행 이력 = 브라우저 저장소 최근 10건 | 무기한 보관 · 누가 언제 되돌렸는지 기록 |
| 0건 로그 = 미리 만든 샘플 CSV를 사람이 업로드 | 각 사 검색 로그 분석에서 집계본을 배치로 수신 |
| 스냅샷을 받으면 그대로 신뢰 | HTTPS 강제 + **서명 검증**. ETag는 변경 감지이지 무결성 검증이 아니다 |
| 부서 = 입력 필드 | 조직 계정·권한 체계 |

`sync()`와 `lookup()`의 로직은 두 경우가 동일하고 바뀌는 것은 전송 계층뿐이다.

## 검증

동작 확인은 아래 순서로 한다. `prototype/router/`에서 두 파일을 탭 두 개로 연다.

1. 앱 탭에서 `k패스카드` 검색 → 안내 없음, 계측에 `캐시 버전: 없음`
1-1. 콘솔 `로그로 후보 찾기` 탭 → `샘플 로그 불러오기` → 미등록 7건과 추천 확인 → `표현 추가` 몇 건
2. 콘솔 탭에서 `계열사 샘플 불러오기` 드롭다운으로 네 양식을 차례로 불러온다 → 미리보기에서 자동·수기 칸 확인 → `기본값 채우기` → `등록 요청` → `일괄 검토 요청` → `일괄 승인` → `승인된 기준 발행`
3. 앱 탭에서 `동기화` → 로그에 `200 OK · 수신 N B · v1` → 같은 검색어에 안내 노출
4. 앱 탭에서 `동기화` 재실행 → `304 Not Modified · 수신 0 B`
5. 앱 선택을 `NH Pay`로 바꾸고 같은 검색 → 안내 대신 미노출 사유 표시
5-1. 네 앱을 차례로 골라 본다 → 헤더 정렬·검색창 형태·칩·강조색이 앱마다 바뀐다. as-is 캡처(`prototype/slides/images/asis-*.jpg`)와 나란히 놓고 대조한다
5-2. 헤더의 `네 앱 비교`를 켠다 → 같은 안내 데이터가 네 디자인으로 그려진다
6. 콘솔에서 `NH농협카드 모바일웹`을 `미사용`으로 바꾸고 재발행 → 앱에서 동기화 → 그 줄이 사라짐
7. 앱 탭에서 `캐시 비우기` → 검색은 정상, 안내만 사라짐
8. 앱 탭에서 `스냅샷 손상시키기` → 안내만 사라지고 검색은 정상(예외 없음) → `동기화` → `200`으로 다시 받아 안내가 되살아남
9. 콘솔에서 아무것도 바꾸지 않고 `승인된 기준 발행` → `바뀐 내용이 없어 발행하지 않았습니다` (버전이 올라가지 않는다)
9-1. 발행된 기준 한 줄을 `삭제` → 확인창이 `앱에 나가 있다`고 알린다 → 지운 뒤 발행 바에 `발행하면 앱에서 1건이 사라집니다`가 뜬다 → `승인된 기준 발행` → 빠지는 기준을 다시 확인받고 발행 → 앱에서 `동기화` → 그 안내가 사라진다
10. 콘솔 `발행 이력`에서 이전 버전 `되돌리기` → 빠지는 기준을 확인하고 진행 → 앱 탭에서 `동기화` → 되돌린 내용이 반영됨

자동 검사는 저장소에 들어 있다. 외부 라이브러리 없이 돌아간다.

```bash
cd prototype/router
node tests.mjs
```

정규화·동기화·조회·미노출·실패 방어·손상 회복·이상 입력·스냅샷 캐시·상태 보고·크기 내성·발행 관문·재발행 차단·발행 이력·이력 비우기·이스케이프·기준 삭제·앱별 디자인 컴포넌트·기기 껍데기 **248개 항목**이며 전부 통과한다. 검사 대상은 화면이 아니라 실제 코드다 — `routing-client.js`와 `app-themes.js`를 직접 불러 쓰고, 발행 관문은 `console.html`에서 함수를 꺼내 확인한다. 브라우저 전역은 검사 파일 안에서 최소한으로 흉내낸다.

디자인 컴포넌트 쪽은 네 가지를 못박는다.

```text
같은 데이터를 넣으면 네 앱의 마크업이 서로 다르다 — 그리고 남의 클래스가 섞이지 않는다
라우터가 준 값(기능명 · 채널 · 역할 · 다음 행동)이 네 앱 모두에서 빠지지 않는다
렌더러가 없거나 예외를 던져도 최소 구현으로 떨어지고 검색은 멈추지 않는다
앱별 강조색이 대비 기준을 지킨다 — 본문용 4.5:1, 면·테두리 3:1 (계산을 검사 안에서 한다)
상태바·내비게이션 바 색이 실측값 그대로다 — 넷이 한 벌로 통일돼 있지 않은 것까지 확인한다
```

마지막 항목은 실측 강조색 셋이 본문 기준에 미달한다는 관찰에서 나왔다. 그 값을 글자에 그대로 쓰지 않도록 검사가 막는다.

콘솔의 CSV 파서와 0건 로그 후보 추천은 아직 이 검사에 없다. 두 기능은 `console.html` 안에 들어 있어 떼어내야 검사할 수 있다. 위 「검증」 절의 수동 절차로 확인한다.

## 고지와 한계

- 이 화면들은 기획 검증용 **목업**이다. 실제 NH농협 서비스가 아니며 NH농협과 무관하다. 실제 계좌·카드 신청은 일어나지 않고 개인정보를 수집하지 않는다.
- as-is 검색 결과는 2026-08-18~20에 실제 앱에서 검색해 기록한 값이다. 출처는 각 파일 주석과 [`docs/NH앱4개_카드검색_as-is결과.md`](../../docs/NH앱4개_카드검색_as-is결과.md)에 있다.
- **안내가 사용자를 실제로 돕는지는 검증하지 않았다.** After 사용성 테스트는 이번 범위에서 제외했다. 제시할 수 있는 수치는 커버리지와 도입 비용이며 사용자 효과가 아니다.
- as-is 데이터는 본인이 직접 검색한 n=1 기록이고, 비교 검색어 확인도 스마트뱅킹 1건뿐이다.
- **스냅샷 무결성을 검증하지 않는다.** 앱은 받은 스냅샷에 서명이나 체크섬을 확인하지 않고, `transports.http()`도 HTTPS를 강제하지 않는다. 이 제품이 하는 일이 `이 업무는 저 채널로 가세요`라고 사용자를 안내하는 것이므로, **스냅샷이 변조되면 그대로 피싱 유도 화면이 된다.** 채널 이름과 다음 행동 문구만 바꾸면 되기 때문이다. 실제 서비스에서는 서명 검증이 필수다.
- **0건 로그를 쌓는 쪽은 구현하지 않았다.** 콘솔이 로그를 받아 등록 후보를 뽑는 것은 실제로 동작하지만, 앱이 0건 검색을 기록해 내보내는 기능은 없다. 샘플 CSV의 검색수는 예시값이고 `86%`도 그 샘플 기준 계산이다.
- **삭제에 이력이 없다.** 지우면 되돌릴 수 없고 누가 언제 지웠는지도 남지 않는다. 발행 스냅샷은 이력에서 되돌릴 수 있지만 등록 목록의 삭제는 되돌릴 수 없다. 권한 분리와 반려도 미구현이다.
- 서버가 없어 여러 기기·여러 사람 간 공유는 되지 않는다.
