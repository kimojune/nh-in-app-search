# ThinkCode 제출 메커니즘 확인

- 확정일: 2026-08-21
- 문서 유형: 결정 기록 (decision-log)

## 결정

이 로컬 저장소·이 세션에서는 ThinkCode `submit_session`을 호출하지 않는다. 실제 제출(과제 마감 시 최종 제출)은 사용자가 ThinkCode 쪽에서 별도로 처리한다. 이 세션의 역할은 (1) 마감일·제출 조건 확인, (2) 사용성 테스트용 프로토타입 제작, (3) ThinkCode 제출용 시작 프롬프트 준비까지로 한정한다.

## 확인된 사실 (`get_active_assignment` 응답 기준, 2026-08-21)

- assignmentId=40, 제목 "[1차 프로젝트] 1차 개인 프로젝트 제출"
- **마감일: 2026-08-27** (기존 로컬 문서는 "미기재"였으나 실제로는 확정돼 있었음)
- **kind = "vibe"** — ThinkCode는 과제를 `ax`(업무자동화)와 `vibe`(AI와 대화하며 결과물을 만드는 과제)로 구분하며, 이 과제는 vibe로 분류돼 있다. PO·기획 트랙이든 개발 트랙이든 관계없이 이 시스템 분류는 제출 방식 기준일 뿐이다.
- **제출 규약(submitProtocol)**: `submit_session`을 호출하면
  1. **그 호출이 실행되는 세션의 대화 기록 파일**(예: `~/.claude/projects/<slug>/*.jsonl`, 또는 Codex의 최근 세션)을 읽는다.
  2. 대화 전체(요약·생략 없이)를 `transcript.turns`에 담는다.
  3. 모델·토큰 사용량 등 통계를 함께 담는다.
  4. 완성된 코드 파일을 `artifacts`에 담는다 — kind=vibe 과제는 이 코드가 ThinkCode 방에 자동으로 들어가 강사가 열람·실행한다.
  5. **어느 세션에서 코드를 만들었는지는 시스템이 강제하지 않는다** — "제출을 실행하는 세션"의 기록이 그대로 쓰일 뿐이다.

## 왜 이게 혼동됐었나

사용자가 "앞으로 ThinkCode에 작업할 거야, pull하면 안돼"라고 말했을 때, 처음엔 "실제 구현은 ThinkCode 쪽 별도 세션에서 진행한다"로 해석해 계획을 세웠다. 이후 실제로는 "사용성 테스트용 프로토타입은 이 세션에서 직접 만들어 Artifact로 배포한다"로 방향이 정정됐다(자세한 내용은 [`사용성테스트_프로토타입_제작방식_확정.md`](./사용성테스트_프로토타입_제작방식_확정.md)).

핵심 교훈: **"구현 장소"와 "제출 실행 장소"는 서로 다른 결정 사항**이다. `pull_files`를 쓰지 말라는 지시는 "ThinkCode에 이미 있는 걸 로컬로 끌어오지 말라"는 뜻일 뿐, 코드를 어디서 짜고 제출을 어디서 실행할지는 별도로 정해야 한다.

## 이번에 정한 역할 분담

| 항목 | 담당 |
|---|---|
| 사용성 테스트용 프로토타입 구현 | 이 세션(Claude Code 로컬) → Claude Artifact로 배포 |
| ThinkCode 제출용 "동작하는 결과물" 구현 | 사용자가 ThinkCode에서 직접, `docs/ThinkCode_시작프롬프트.md`를 시작점으로 사용 |
| `submit_session` 호출(실제 제출) | 이 세션에서 하지 않음 — 사용자가 ThinkCode 쪽 작업이 끝난 뒤 그쪽에서 처리 |
| `pull_files`/`push_files` | 이 세션에서 사용하지 않음(사용자 지시) |

## 참고

- `pull_files` 사용 금지 지시는 로컬 Claude 자동 메모리(`feedback-thinkcode-workflow.md`)에도 저장돼 있으나, git으로는 옮기지 않기로 함(2026-08-21 재확인 — 다른 에이전트·다른 컴퓨터로 전달할 만큼 위험도가 높지 않다고 판단).
