## 결정 일자

2026-08-24

## 결정 주제

제출용 결과물을 화면 전환 목업이 아니라 **실제로 동작하는 크로스 앱 라우터**로 만든다. 이 결정은 [`기능콘셉트_범용도구화_확정.md`](./기능콘셉트_범용도구화_확정.md)에서 작업량을 이유로 기각했던 `완전 범용화` 대안을 되살리는 것이다.

## 배경

2026-08-21에는 세 가지 대안 중 `가벼운 범용 프레이밍`을 채택하고, `회사가 앱·기능·매핑 규칙을 입력하면 실제로 크로스앱 안내가 자동 생성되는 규칙엔진까지 구현`하는 안은 **마감까지 6일, 작업량이 너무 큼**을 이유로 기각했다.

2026-08-24에 사용자가 "실제로 작동하는 개념의 서비스를 만들고 싶다"고 방향을 바꿨다. 동시에 설계 제약을 하나 제시했다 — **계열사 앱이 부담하는 리소스를 최대한 줄일 것.**

## 왜 이번에는 가능한가

기각 당시의 `규칙엔진`과 지금 만든 것은 범위가 다르다.

| 2026-08-21에 상상한 것 | 2026-08-24에 만든 것 |
|---|---|
| 검색 결과를 자동 생성하는 규칙 엔진 | 검색은 손대지 않음. 담당 채널 기준만 배포 |
| 서버·DB·권한 시스템 | 서버 없음. 브라우저 저장소로 연동 |
| 매칭·랭킹 로직 | 정규화된 사전 조회 한 번 |

범위를 좁히니 이틀 안에 들어왔다. **기각 판단이 틀렸다기보다, 기각 대상이던 범위와 지금 범위가 다르다.**

## 최종 결정

`prototype/router/`에 실제로 동작하는 구현을 둔다.

```text
[계열사 담당자]      [라우터 콘솔]           [발행 스냅샷]          [계열사 앱]
상품·업무 데이터  →  자동 매핑           →  routing-index.json →  routing-client.js
내보내기(CSV)        역할·다음 행동만 수기     version + etag        sync()  하루 1회
                     정규화·표현 확장         index / functions     lookup() 검색마다
                     미노출 지정              (승인된 것만)          네트워크 0
                     중앙 승인 후 발행
```

핵심 설계는 **지능을 중앙에 두고 말단은 사전 조회만 하게 하는 것**이다. 앱은 동의어 판단도, 담당 채널 판단도, 어느 앱에서 안내를 숨길지도 결정하지 않는다.

### 등록은 양방향이다

- **밀어 넣기**: 계열사가 이미 가진 데이터를 내보내 올린다. 회사 데이터에 없어서 손으로 채우는 값은 `채널 역할`과 `다음 행동` 두 가지뿐이다.
- **끌어오기**: 앱의 검색 결과 0건 로그를 올리면 라우터가 등록할 표현을 역으로 찾아낸다. 승인된 기준에 표현을 추가하면 상태가 `검토 중`으로 되돌아가 재승인을 받는다.

## 결정 이유

- 계열사가 감독 체계가 다른 별도 법인이므로, 도입에 손이 많이 가면 실제로 채택되지 않는다. `앱은 조회만, 계열사는 내보내기만`이 이 도구가 성립하는 조건이다.
- 과제 평가의 `동작·완성도`(20점)와 제출물 요건 `동작하는 결과물`을 목업으로는 채우기 어렵다.
- 담당 채널은 검색 데이터가 아니라 조직 데이터다. 어느 검색 엔진 사전에도 그 값이 없으므로 별도 기준이 필요하다는 논지가 구현으로 증명된다.

## 여전히 하지 않는 것

- 실제 NH 앱·백엔드·거래·로그인·딥링크 구현
- 검색 엔진의 색인·랭킹·동의어 사전 등 검색 품질 자체
- 권한이 분리된 승인 워크플로와 감사 로그
- 여러 기기·여러 사람 간 공유 (서버가 없다)
