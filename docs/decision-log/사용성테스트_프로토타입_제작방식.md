# 사용성 테스트 프로토타입 제작 방식

- 작성일: 2026-08-21
- 상태: 무효 — 2026-08-28 기각. 아티팩트를 제작하기는 했으나 배포하지 않았고 이 방식으로 검증하지 않았다
- 의도 확인: 확인함 (2026-08-28)
- 문서 유형: 종료 시점 스냅샷 — 2026-08-28 프로젝트 종료 이후 갱신하지 않는다

## 2026-08-22 정정 — 현재 유효한 결정

기존 Claude Artifact는 ‘공통 목적지 자동 이동’ 전제를 검증하기 위해 만든 과거 결과물로 보존한다. 현재 해결안은 담당 채널과 역할을 안내해 사용자가 다음 행동을 결정하게 하는 방식이므로, 기존 프로토타입을 현재 After 검증물로 사용하지 않는다.

현재 검증은 두 자료로 나눈다.

- 자유 탐색 Before: 일반 은행 앱 사용자가 제한 없이 K-패스카드 처리 경로를 찾게 하고 포털 선시작, 앱 시작 후 포털 이탈, 전체 외부 검색 의존을 관찰한다.
- 안내형 After: 수정 프로토타입에서 외부 재검색·진행자 도움 없이 올바른 담당 채널과 다음 행동을 결정하는지 확인한다.

두 조건은 매체와 종료점이 다르므로 직접 개선율을 계산하지 않는다. 같은 매체의 엄격한 전후 비교가 필요하다면 별도의 실험 설계를 추가해야 한다. 아래 결정은 2026-08-21 당시 자동 이동형 프로토타입 제작 이력으로 남긴다.

## 결정

B축 개선안을 참가자가 실제로 조작해보는 사용성 테스트 프로토타입을 **ThinkCode가 아니라 이 세션에서 직접 제작**해 **Claude Artifact로 배포**한다. Before와 After를 **같은 참가자·같은 매체(이 프로토타입) 안에서 순서를 바꿔가며(카운터밸런싱)** 겪게 한다.

## 배경

`docs/B축_MVP_설계.md`는 화면 설계까지 끝냈지만, "이 개선안을 참가자가 직접 눌러보게 하려면 어떤 형태로 만들어야 하는가"는 별도 문제였다. 처음엔 ThinkCode에 구현을 맡기는 시작 프롬프트(`_process/_done/docs/ThinkCode_시작프롬프트.md`)를 준비했으나, 이후 사용성 테스트에 쓸 실동작 프로토타입을 어떻게 확보할지 논의가 이어졌다.

## 검토한 대안

|---|---|---|
| Figma 클릭형 프로토타입 (새로 그리기) | 화면 11개를 Figma에서 새로 제작 | 반나절~1일 소요 추정, 무료 플랜에서 공유 링크가 프로토타입만 보여주는지 편집화면까지 노출하는지 불확실(확인 못함) |
| Figma (스크린샷을 배경으로 얹고 핫스팟만 추가) | Before는 실제 스크린샷을 배경 이미지로 쓰고 클릭 가능한 투명 영역만 추가 | 작업량은 줄지만, 실제 타이핑 검색 같은 동적 상호작용은 표현하기 어려움. 여전히 Figma 무료 플랜 공유 방식 확인 필요 |
| Figma + Maze 연동 | Maze의 "Website Test" 기능은 코드 삽입 없이 호스팅된 URL이면 테스트를 만들 수 있다고 웹 검색으로 확인됨 | 가능성 있으나 무료 플랜 참가자 한도가 자료마다 달라 불명확(확인 못함) |
| ThinkCode HTML → 무료 호스팅(Netlify Drop 등) → Maze 연동 | 비개발자가 5분 안에 할 수 있는 무료 호스팅 방법들을 조사함(Netlify Drop, Tiiny.host 등) | 단계가 여러 개(호스팅 → Maze 연동 → 무료 한도) 겹쳐 검증 안 된 지점이 누적됨 |
| **이 세션에서 직접 제작 + Claude Artifact 배포** | 외부 도구 없이 즉시 공유 가능한 링크 확보 | **채택** — 위 대안들의 불확실성(무료 플랜 한도, 공유 방식)을 전부 우회 |

## 핵심 방법론적 근거 — 왜 Before/After를 같은 매체에서 봐야 하는가

Before 데이터(as-is 조사, A축 테스트)는 모두 **실제 네이티브 앱**에서 나온 것이다. 만약 After만 웹 프로토타입으로 만들어 테스트하면, "소요시간이 줄었다"는 결과가 "동의어 매핑이 좋아져서"가 아니라 "그냥 웹 링크라 로그인·설치가 없어서 빨랐던 것"일 수 있다 — 매체 차이가 개선 효과처럼 보이는 왜곡이 생긴다.

이 문제는 피할 수 없다 — NH가 실제로 이 기능을 만든 게 아니므로 After를 실제 네이티브 앱 안에서 테스트할 방법이 없다. 그래서 해법은 "매체를 실제 앱으로 맞추는 것"이 아니라 **"Before와 After 둘 다 같은 매체(이 프로토타입) 안에서, 같은 참가자에게 순서를 바꿔가며 겪게 해서 매체 차이를 상쇄하는 것"**이다. 참가자 절반은 Before→After, 절반은 After→Before로 진행해 순서(학습) 효과도 함께 확인한다.

## 로깅 방식

참가자 수가 적어(4~8명) 서버 집계는 불필요하다고 판단해, 프로토타입 자체가 클라이언트 측에서 소요시간·검색 시도·성공 여부를 계산해 단계 종료 시 요약 화면으로 보여주고, 진행자가 관찰 기록표에 옮겨 적는 방식을 택했다. 이는 A축 테스트의 알려진 한계("관찰 정확도가 진행자 기록에 의존" — `K패스카드_과제수행테스트_진행안.md`의 "A축 한계 종합" 8번)를 부분적으로 보완한다.
