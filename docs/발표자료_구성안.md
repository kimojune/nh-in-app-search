# 발표 자료 구성안

> **발표 구성을 한 번 갈아엎은 기록이다.** 최종 구성은 아래 「최종 구성」 절이고,
> 장별로 무엇을 말할지의 단일 기준은 [`발표_스피커노트.md`](./발표_스피커노트.md)다.
> 아래 「부록」의 7항목은 재편하기 전 계획으로, **무엇이 어떻게 바뀌었는지 보이도록** 남겨 뒀다.

- 최종 수정일: 2026-08-26
- 문서 유형: 종료 시점 스냅샷 — 이후 갱신하지 않는다
- 발표: 2026-08-26 · 최대 7분 (최종 구성 300초)
- 제출: 2026-08-27 (ThinkCode)

**결론을 먼저 말하고, 본문은 피벗 서사로 간다.** 짧은 발표에서 `효과는 못 쟀다`를 뒤에 두면 듣는 사람이 앞부분을 믿었다가 배신당한다. 먼저 깔면 나머지가 전부 `그럼 무엇을 했나`로 읽힌다.

본문 흐름은 [`PROJECT_GUIDE.md`](../PROJECT_GUIDE.md)에 확정된 피벗 서사를 그대로 따른다.

> `초기 저빈도 기능 탐색 가설 → 설문·행동에서 포털 대안 발견 → NH의 슈퍼앱·운영 주체·기술·사용성 제약 조사 → 완전 통합 대신 최소 담당 채널 안내 방식 제안`

이 문서는 **무엇을 말할지와 근거가 어디 있는지**를 적는다. 슬라이드 문장은 직접 쓴다.

## 파일과 빌드

```text
prototype/slides/*.dc.html      슬라이드 소스 아홉 장. 고치는 곳은 여기다
prototype/slides/canvas.json    순서
prototype/slides/build.mjs      배포본을 만드는 스크립트
prototype/slides/발표자료.html   배포본. 발표에서 띄우는 파일 — 손으로 고치지 않는다
prototype/slides/preview.html   소스 아홉 장을 한 화면에 늘어놓는 미리보기
```

소스를 고친 뒤 반드시 다시 만든다. 이미지까지 파일 안에 박히므로 배포본 하나만 있으면 발표가 된다.

```bash
cd prototype/slides
node build.mjs
```

**손으로 배포본을 고치지 않는다.** 소스와 배포본이 갈라지면 어느 쪽이 맞는지 알 수 없고, 발표에서 띄우는 것은 배포본이라 그 사고는 발표 자리에서 드러난다.

## 부록 — 이전 7항목 계획 (2026-08-25 기준 · 보존)

아래는 실무 단계로 재편하기 전의 계획이다. **최종 구성과 맞지 않으므로 참조하지 않는다.**

### 시간 배분

```text
1  결론 먼저                     25초
2  가설과 반증                   50초
3  그래도 남는 것                30초   ← 6장에 시간을 주려고 줄임
4  왜 통합이 아닌가              35초
5  최소 안내로 좁혔다 + 구조      50초
6  지표 구조                     35초
7  ▶ 시연                       50초
8  못 한 것과 다음               40초
                                ─────
                                300초 (5분)
```

**(2026-08-25 추가) 6장 지표 구조**는 슬라이드가 과제 평가항목 「성능 지표」와 연결되지 않고 지표 설명이 없다는 지적에서 추가했다. 1차 KPI·보조 지표·가드레일 구조를 보여주고, 「지금까지 측정된 것」(문제 크기·도입 가능성)과 안내의 효과는 다른 층이라는 점을 여기서 먼저 밝힌다. 근거는 [`B축_MVP_설계.md`](./B축_MVP_설계.md)의 「검증 기준」. 시간 배정과 실제 말할 문장은 아직 직접 작성 전이다.

**`설계 판단과 맞바꾼 것`을 따로 두지 않는다.** 피벗 서사 자체가 그것이다 — 완전 통합 대신 최소 안내로 좁힌 것이 이 프로젝트에서 가장 큰 맞바꿈이다. A안 기각은 문서와 질의응답으로 넘긴다.

**안정성과 재현성은 시연 안에서 말한다.** `이 관문은 시연하다 찾아서 막은 것`이 별도 장으로 말하는 것보다 강하다.

### 6. 지표 구조 · 35초

**말할 것**

**(2026-08-26 갱신)** 주 KPI 문구에 `인앱검색만으로`를 넣어 **무엇이 문제를 풀었는지**를 명시했다. **판정 범위는 그대로다** — `다음 행동`은 빼지 않았다.

```text
먼저 밝힌다   안내의 효과 자체는 아직 측정되지 않았다
             실험군 2명뿐이고 대조군이 없다

1차 KPI (검증 예정)
  외부 재검색이나 진행자 도움 없이 인앱검색만으로
  올바른 담당 채널과 다음 행동을 결정한 참가자 비율
  ← 안내 카드의 한 줄("이 채널에서 무엇을 할 수 있는지")이
    실제로 전달됐는지를 재는 조건이다

보조 지표 (검증 예정)
  올바른 채널 선택률 · 올바른 다음 행동 설명률 · 결정까지 걸린 시간
  검색어 재입력 횟수 · 외부 검색·도움 요청 비율 · 채널 역할 오해율

가드레일 (관찰값 있음)
  잘못된 채널을 확신하는 비율        15명 중 7명   (인식설문)
  복수 완료 채널로 결정을 보류한 비율  2명 중 2명    (실험군 관찰)
```

**왜 두 조건을 다 요구하나** — 안내를 노출하는 조건 자체가 「다음 행동을 판단하기 어렵다」(`B축_MVP_설계.md` 노출 조건 3번)이고, 콕뱅크 79건 사례가 「앱은 맞게 갔으나 그 안에서 무엇을 할지 몰라 이탈한」 경우다. **판정에서 다음 행동을 빼면 기능이 해결하려는 문제를 판정이 보지 못한다.**

**목표와 판정은 같다** — 기능이 내놓는 것이 `어느 채널 + 거기서 무엇을`이므로, 판정도 그 둘이 전달됐는지를 본다.

**남은 위험** — 표본 5~8명에서 조건 2개를 모두 요구하면 주 KPI 성공이 0~1건으로 깔릴 수 있다. 보조 지표 `올바른 채널 선택률`과 `올바른 다음 행동 설명률`을 반드시 함께 집계해 **어느 조건에서 막혔는지 분리**한다.

**꺼내지 않는 것** — 실험군 2명의 다음 행동 답변(`케이패스`, `신청`)은 **판정하지 않는다.** 그 관찰의 문항과 진행 방식이 어느 문서에도 남아 있지 않아 **어떤 판정선도 적용할 수 없다**(원자료는 채팅 JSON에만 있다). `사용성테스트_B축프로토타입_진행안.md`의 「다음 행동의 판정선」은 **아직 시행하지 않은 After 테스트의 절차**이므로 이 관찰에 소급 적용하지 않는다. **성공·실패 어느 쪽으로도 세지 않는다.**

**진짜 마찰은 다른 데 있었다** — 2명 모두 완료 채널 두 개 사이를 왕복했다. `B축_MVP_설계.md`가 미확정으로 남겨둔 「복수 채널의 노출 개수·정렬 우선순위」가 실제 마찰이라는 것이 관찰로 확인됐다.

**화면** — 3단 구성(1차 KPI · 보조 지표 · 가드레일). 슬라이드: `prototype/slides/Built.dc.html`의 「어떻게 잴 것인가」 열.

**근거** — [`B축_MVP_설계.md`](./B축_MVP_설계.md)의 「검증 기준」·「지금까지 측정된 것」.

**이 장의 값어치** — 과제 평가항목 「성능 지표」와 발표를 직접 연결하는 장이다. 숫자 자체보다 **무엇을 지표로 삼았고 그중 뭐가 아직 안 재졌는지**를 분명히 하는 것이 목적이다.

**조심할 것** — 가드레일의 `15명 중 7명`은 자기보고·5지선다라 재인(recognition) 한계가 있다. `2명 중 2명`은 무인 진행이고 대조군이 없다. 둘 다 안내 효과의 대체 증거로 과장하지 않는다.

### 7. 시연 · 50초

**한 장면만 한다.** 0건에서 안내가 붙는 지점이 이 기획의 전부다.

```text
1  앱 탭     콕뱅크에서 `k패스카드` 검색 → 0건, 안내 없음
2  콘솔 탭   계열사 샘플 불러오기 → 등록 요청 → 일괄 검토 요청
             → 일괄 승인 → 승인된 기준 발행
3  앱 탭     동기화 → 200 OK → 같은 검색어에 안내가 뜬다
4  앱 탭     동기화 한 번 더 → 304 Not Modified · 수신 0 B
```

**돌리면서 한 줄 말한다**

> 승인을 건너뛰면 빈 기준이 나가서, 앱은 200 OK를 받고도 아무 안내를 못 띄웁니다.
> **시연하다 그걸 겪고 이 관문을 막았습니다.**

**준비**

```text
prototype/router/console.html
prototype/router/bank-app.html      헤더 오른쪽 `발표 모드` 버튼
```

두 파일을 탭 두 개로 미리 열고, 발표 모드를 켠 뒤 화면 크기를 확인한다. 콘솔은 `전체 초기화`로 깨끗한 상태에서 시작한다.

**아껴둘 것** — 되돌리기, 스냅샷 손상 후 회복. 시간이 남거나 질문이 나오면 보여준다.

### 예상 질문과 답

| 질문 | 답할 것 |
|---|---|
| 효과를 못 쟀는데 좋은 줄 어떻게 아나 | **모른다.** 근거는 문제의 크기와 도입 비용까지다. 그 구분을 1장에서 먼저 밝혔고, 6장에서 어떤 지표가 아직 검증 예정인지 보여준다 |
| 왜 하필 NH인가 | 2장. 상호금융·은행·페이로 조직이 쪼개진 사례라서 골랐다. 문제는 저빈도 금융 기능 탐색 전반이고, NH 4개 앱은 첫 적용 사례다 |
| 그냥 앱을 합치면 되지 않나 | 4장. 운영 주체·기술·사용성. 합쳐도 다 못 합친다 |
| 포털이 대체하는데 왜 만드나 | 3장. 회사가 그 지점부터 통제력을 잃는다 |
| 계열사가 왜 깔아주나 | 이미 크로스링크를 만들어 뒀다. 없는 건 협조 의사가 아니라 정밀도다 |
| 검색을 고치면 되지 않나 | 담당 채널은 검색 데이터가 아니라 조직 데이터다. 어느 검색 사전에도 그 값이 없다 |
| 왜 앱이 중앙에 물어보지 않나 | 검색당 0 B가 사라지고, 중앙이 멈추면 앱 검색도 멈추고, 검색어가 다른 법인으로 넘어간다 |
| 자동 이동은 왜 안 하나 | 확정 사항이다. 딥링크 백엔드는 범위 밖이다 |
| `86%`는 실측인가 | **아니다.** 샘플 로그 기준 계산이다. 계산은 재현되지만 입력이 예시값이다 |
