# 인앱 검색 도메인 학습 기록

- 최종 수정일: 2026-08-23
- 문서 유형: 계속 갱신
- 상태: 학습 진행 중
- 현재 위치: 문제 구조화를 위한 도메인 리서치 — 검색 대상·검색어 매칭 학습 완료, 검색 관련도 학습 전

## 목적

인앱 검색 기반 서비스 라우팅을 설계하기 전에 PM 관점에서 필요한 검색 개념을 학습하고, 실제로 이해가 확인된 내용과 아직 학습하지 않은 내용을 구분한다. 사용자가 다음 작업 단계로 넘어가겠다고 판단하기 전에는 이 기록을 분석 프레임워크나 확정 정책으로 취급하지 않는다.

## 학습 진행 방식

사용자는 한 번에 많은 개념을 읽는 방식보다 다음 순서로 학습하기를 원한다.

```text
개념 하나 설명
→ NH 또는 금융 앱 사례 하나 적용
→ 사용자가 직접 분류·판단
→ 이해 확인과 오개념 교정
→ 다음 개념
```

다음 에이전트는 아래 원칙을 따른다.

- 문서를 먼저 작성하고 학습을 따라오게 하지 않는다.
- 한 번에 핵심 개념 하나만 다룬다.
- 쉬운 한국어 뒤에 전문 용어를 괄호로 함께 쓴다. 예: 검색 결과 없음 비율(Zero Results Rate, ZRR).
- 사용자의 답을 맞고 틀림으로만 판정하지 않고, 관찰 사실·해석·추정이 어디서 섞였는지 설명한다.
- 화면 관찰만으로 NH 내부 검색 구조를 확정하지 않는다.
- 사용자가 다음 단계로 넘어가겠다고 말할 때 학습 결과를 분석 문서로 전환한다.

## 실무 단계에서의 현재 위치

현재 학습은 제품 발견(Product Discovery) 안의 문제 발견·정의(Problem Discovery & Definition)에 속한다.

```text
제품 발견(Product Discovery)
└─ 문제 발견·정의(Problem Discovery & Definition)
   ├─ 도메인 리서치(Domain Research)                 ← 현재
   ├─ 문제 구조화(Problem Structuring)
   │  └─ 분석 프레임워크 수립(Analytical Framework Design)
   ├─ 가설 수립(Hypothesis Formulation)
   └─ 문제 검증(Problem Validation)
```

- 도메인 리서치: 인앱 검색이 어떤 구조와 용어로 작동하는지 학습
- 문제 구조화: `검색이 불편하다`를 검색 대상·매칭·관련도·채널 연결·과업 성공 문제로 분해
- 분석 프레임워크: 구조화한 문제를 NH 앱에 동일하게 적용할 비교 항목과 판정 기준

이 위계는 업계의 단일 공식 표준이 아니라, 서비스 기획·PM·PO가 공유하는 실무 개념을 현재 프로젝트에 맞게 정리한 작업 체계다.

## 체화가 확인된 내용 1 — 검색 대상

검색 대상(Search Scope)은 해당 검색창이 어떤 종류의 정보를 찾을 수 있게 구성되어 있는지를 뜻한다.

### 결과 유형 구분

| 결과 유형 | 판단 질문 | 예시 |
|---|---|---|
| 상품(Product) | 무엇을 가입·발급하는가? | K-패스카드, 주택청약종합저축 |
| 업무(Task) | 무엇을 하려는가? | 자동이체 해지, 통장사본 발급 |
| 메뉴(Menu) | 다른 기능으로 들어가는 경로인가? | 상품몰, 인증/보안 |
| 콘텐츠(Content) | 설명이나 도움말을 읽는가? | 대출금리 안내, K-패스카드 FAQ |

### 사용자가 직접 확인한 이해

- `주택청약종합저축`, `올바른 FLEX 카드`를 상품으로 분류했다.
- `자동이체 해지`, `통장사본 발급`을 업무로 분류했다.
- `상품몰`을 메뉴, `대출금리 안내`와 FAQ를 콘텐츠로 분류했다.
- `인증/보안`은 처음 업무로 보았으나, 구체적 행동이 없는 상위 경로이므로 메뉴·카테고리에 가깝다는 차이를 이해했다.
- `NH농협카드`처럼 문구만으로 유형이 불명확하면 실제 카드 이름인지, 카드 목록·브랜드·외부 채널인지 클릭 후 목적지(Destination)를 확인해야 한다고 판단했다.
- `메뉴 1건, 상품 0건`인 사례에서 “표현은 관련 메뉴에 연결되지만 개별 카드 상품은 나타나지 않는다”는 제한된 결론을 선택했다.

### 핵심 원칙

```text
앱 안에 기능이 없음
≠ 앱 검색 대상에 기능이 없음
≠ 검색 대상에는 있지만 특정 표현으로 찾지 못함
```

개별 상품 한 건의 실패를 상품군 전체로 일반화하지 않는다. 다른 실제 상품명을 비교 검색어(Control Query)로 사용해 가능한 원인을 좁힌다.

## 체화가 확인된 내용 2 — 검색어 매칭

검색어 매칭(Query Matching)은 사용자가 입력한 표현과 검색 대상 데이터를 어떤 기준으로 연결하는지를 뜻한다.

| 개념 | 의미 | 예시 |
|---|---|---|
| 정확 일치(Exact Match) | 등록 표현과 정확히 일치 | `K-패스카드` |
| 부분 일치(Partial Match) | 일부 단어·문자가 겹침 | `카드` → 보안카드·카드 신청 |
| 표기 정규화(Query Normalization) | 띄어쓰기·하이픈·대소문자 같은 표기 차이 처리 | `카드 신청` ↔ `카드신청` |
| 동의어 매칭(Synonym Matching) | 의미가 가까운 표현 연결 | `해지` ↔ `취소` |
| 의도 매핑(Intent Mapping) | 설명형 표현을 실제 업무 목적에 연결 | `통장 만들기` → 계좌 개설 |
| 오타 허용(Typo Tolerance) | 철자가 조금 달라도 가까운 표현 검색 | `K-페스카드` |

### 사용자가 직접 확인한 이해

- `K-패스카드`가 검색되므로 상품이 검색 대상에는 포함됐다고 판단했다.
- `K패스카드`만 실패하면 하이픈 차이를 처리하지 못한 정규화 문제일 가능성을 이해했다.
- `k-패스카드` 성공은 영문 대소문자 정규화가 작동한다는 관찰로 구분했다.
- `케이패스카드` 실패는 단순 표기 차이가 아니라 `K–케이` 동의어 매칭 문제일 수 있음을 이해했다.
- `카드 신청–카드신청`, `NH Pay–nh pay`를 정규화로 분류했다.
- `계좌 개설–통장 만들기`를 의도 매핑, `자동이체 해지–자동이체 취소`를 동의어 매칭으로 분류했다.
- 언어적으로 비슷해도 실제 금융 업무가 다르면 같은 동의어로 묶으면 안 된다는 정책상 주의를 확인했다.

## 노출됐지만 학습 완료로 보지 않는 내용

### 검색 지표

다음 용어는 설명과 간단한 확인을 진행했지만, 현재 우선 학습 범위 네 가지를 다시 한 개념씩 진행하기로 했으므로 완료 항목으로 올리지 않는다.

- 검색 결과 없음 비율(Zero Results Rate, ZRR)
- 검색 결과 클릭률(Click-Through Rate, CTR)
- 전환율(Conversion Rate, CVR)
- 검색 관련도(Search Relevance)
- 과업 성공률(Task Success Rate)

사용자는 다음 구분을 이해했다.

```text
결과 유무 ≠ 관련도
클릭 ≠ 과업 성공
채널 식별 ≠ 신청 완료
직접 KPI ≠ 후행 사업 성과
```

특히 결과가 30건이어도 전부 무관하면 ZRR상 0건 실패는 아니지만, 관련도와 사용자 과업은 실패할 수 있다는 점을 교정했다.

### 가설 작성

가설 수립(Hypothesis Formulation)과 반증 가능성(Falsifiability)을 한 차례 학습했지만 너무 빠르게 많은 내용을 접해 체화되지 않았다고 사용자가 판단했다. 따라서 다음 에이전트는 곧바로 가설 문서를 만들거나 가설 작성을 다시 요구하지 않는다.

사용자가 `카드신청`의 무관 결과를 보고 “올원뱅크에서는 카드 신청을 담당하지 않는다”고 추정한 사례에서, 검색 매칭 관찰과 서비스 담당 범위 가설이 섞일 수 있음을 확인했다. 검색 관련도와 과업 성공까지 학습한 뒤 가설 작성으로 돌아간다.

## 다음 학습

### 바로 이어서 할 개념

**검색 관련도(Search Relevance)**

학습 목표:

1. 결과 존재와 관련 결과 노출을 구분한다.
2. 오탐 결과(False Positive)와 결과 순위(Result Position)를 이해한다.
3. 검색어 매칭 문제와 검색 관련도 문제를 구분한다.
4. NH올원뱅크의 `카드신청` 무관 결과 사례를 직접 분류한다.

검색 관련도가 체화되면 다음으로 과업 성공(Task Success)을 학습한다. 두 개념까지 끝난 뒤 검색 지표와 가설 작성으로 돌아간다.

## 단계 전환 조건

사용자가 아래 네 가지를 NH 사례에서 스스로 구분하고 “다음 단계로 넘어가자”고 결정하면 학습 결과를 NH 앱 비교용 분석 프레임워크로 문서화한다.

- 검색 대상(Search Scope)
- 검색어 매칭(Query Matching)
- 검색 관련도(Search Relevance)
- 과업 성공(Task Success)
