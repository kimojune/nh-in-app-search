# 인앱 검색 도메인 학습 기록

- 최종 수정일: 2026-08-24
- 문서 유형: 계속 갱신
- 상태: 학습 항목 완료 / 단계 전환 대기
- 현재 위치: 문제 구조화를 위한 도메인 리서치 — 계획한 학습 항목 6개 전부 완료. 사용자의 단계 전환 선언 대기

## 목적

인앱 검색 기반 서비스 라우팅을 설계하기 전에 PM 관점에서 필요한 검색 개념을 학습하고, 실제로 이해가 확인된 내용과 아직 학습하지 않은 내용을 구분한다. 사용자가 다음 작업 단계로 넘어가겠다고 판단하기 전에는 이 기록을 분석 프레임워크나 확정 정책으로 취급하지 않는다.

## 학습 진행 방식

사용자는 한 번에 많은 개념을 읽는 방식보다 다음 순서로 학습하기를 원한다.

```text
개념 하나 설명
→ NH 또는 금융 앱 사례 하나 적용
→ 사용자가 직접 분류·판단
→ 이해 확인과 오개념 교정
→ 다음 개념
```

다음 에이전트는 아래 원칙을 따른다.

- 문서를 먼저 작성하고 학습을 따라오게 하지 않는다.
- 한 번에 핵심 개념 하나만 다룬다.
- 쉬운 한국어 뒤에 전문 용어를 괄호로 함께 쓴다. 예: 검색 결과 없음 비율(Zero Results Rate, ZRR).
- 사용자의 답을 맞고 틀림으로만 판정하지 않고, 관찰 사실·해석·추정이 어디서 섞였는지 설명한다.
- 화면 관찰만으로 NH 내부 검색 구조를 확정하지 않는다.
- 사용자가 다음 단계로 넘어가겠다고 말할 때 학습 결과를 분석 문서로 전환한다.

## 실무 단계에서의 현재 위치

현재 학습은 제품 발견(Product Discovery) 안의 문제 발견·정의(Problem Discovery & Definition)에 속한다.

```text
제품 발견(Product Discovery)
└─ 문제 발견·정의(Problem Discovery & Definition)
   ├─ 도메인 리서치(Domain Research)                 ← 현재
   ├─ 문제 구조화(Problem Structuring)
   │  └─ 분석 프레임워크 수립(Analytical Framework Design)
   ├─ 가설 수립(Hypothesis Formulation)
   └─ 문제 검증(Problem Validation)
```

- 도메인 리서치: 인앱 검색이 어떤 구조와 용어로 작동하는지 학습
- 문제 구조화: `검색이 불편하다`를 검색 대상·매칭·관련도·채널 연결·과업 성공 문제로 분해
- 분석 프레임워크: 구조화한 문제를 NH 앱에 동일하게 적용할 비교 항목과 판정 기준

이 위계는 업계의 단일 공식 표준이 아니라, 서비스 기획·PM·PO가 공유하는 실무 개념을 현재 프로젝트에 맞게 정리한 작업 체계다.

## 체화가 확인된 내용 1 — 검색 대상

검색 대상(Search Scope)은 해당 검색창이 어떤 종류의 정보를 찾을 수 있게 구성되어 있는지를 뜻한다.

### 결과 유형 구분

| 결과 유형 | 판단 질문 | 예시 |
|---|---|---|
| 상품(Product) | 무엇을 가입·발급하는가? | K-패스카드, 주택청약종합저축 |
| 업무(Task) | 무엇을 하려는가? | 자동이체 해지, 통장사본 발급 |
| 메뉴(Menu) | 다른 기능으로 들어가는 경로인가? | 상품몰, 인증/보안 |
| 콘텐츠(Content) | 설명이나 도움말을 읽는가? | 대출금리 안내, K-패스카드 FAQ |

### 사용자가 직접 확인한 이해

- `주택청약종합저축`, `올바른 FLEX 카드`를 상품으로 분류했다.
- `자동이체 해지`, `통장사본 발급`을 업무로 분류했다.
- `상품몰`을 메뉴, `대출금리 안내`와 FAQ를 콘텐츠로 분류했다.
- `인증/보안`은 처음 업무로 보았으나, 구체적 행동이 없는 상위 경로이므로 메뉴·카테고리에 가깝다는 차이를 이해했다.
- `NH농협카드`처럼 문구만으로 유형이 불명확하면 실제 카드 이름인지, 카드 목록·브랜드·외부 채널인지 클릭 후 목적지(Destination)를 확인해야 한다고 판단했다.
- `메뉴 1건, 상품 0건`인 사례에서 “표현은 관련 메뉴에 연결되지만 개별 카드 상품은 나타나지 않는다”는 제한된 결론을 선택했다.

### 핵심 원칙

```text
앱 안에 기능이 없음
≠ 앱 검색 대상에 기능이 없음
≠ 검색 대상에는 있지만 특정 표현으로 찾지 못함
```

개별 상품 한 건의 실패를 상품군 전체로 일반화하지 않는다. 다른 실제 상품명을 비교 검색어(Control Query)로 사용해 가능한 원인을 좁힌다.

## 체화가 확인된 내용 2 — 검색어 매칭

검색어 매칭(Query Matching)은 사용자가 입력한 표현과 검색 대상 데이터를 어떤 기준으로 연결하는지를 뜻한다.

| 개념 | 의미 | 예시 |
|---|---|---|
| 정확 일치(Exact Match) | 등록 표현과 정확히 일치 | `K-패스카드` |
| 부분 일치(Partial Match) | 일부 단어·문자가 겹침 | `카드` → 보안카드·카드 신청 |
| 표기 정규화(Query Normalization) | 띄어쓰기·하이픈·대소문자 같은 표기 차이 처리 | `카드 신청` ↔ `카드신청` |
| 동의어 매칭(Synonym Matching) | 의미가 가까운 표현 연결 | `해지` ↔ `취소` |
| 의도 매핑(Intent Mapping) | 설명형 표현을 실제 업무 목적에 연결 | `통장 만들기` → 계좌 개설 |
| 오타 허용(Typo Tolerance) | 철자가 조금 달라도 가까운 표현 검색 | `K-페스카드` |

### 사용자가 직접 확인한 이해

- `K-패스카드`가 검색되므로 상품이 검색 대상에는 포함됐다고 판단했다.
- `K패스카드`만 실패하면 하이픈 차이를 처리하지 못한 정규화 문제일 가능성을 이해했다.
- `k-패스카드` 성공은 영문 대소문자 정규화가 작동한다는 관찰로 구분했다.
- `케이패스카드` 실패는 단순 표기 차이가 아니라 `K–케이` 동의어 매칭 문제일 수 있음을 이해했다.
- `카드 신청–카드신청`, `NH Pay–nh pay`를 정규화로 분류했다.
- `계좌 개설–통장 만들기`를 의도 매핑, `자동이체 해지–자동이체 취소`를 동의어 매칭으로 분류했다.
- 언어적으로 비슷해도 실제 금융 업무가 다르면 같은 동의어로 묶으면 안 된다는 정책상 주의를 확인했다.

## 체화가 확인된 내용 3 — 검색 관련도

검색 관련도(Search Relevance)는 결과가 나왔는지가 아니라, 나온 결과가 사용자가 찾던 것과 맞는지를 뜻한다.

| 개념 | 의미 |
|---|---|
| 오탐 결과(False Positive) | 검색에는 걸렸으나 사용자 목적과 무관한 결과 |
| 결과 순위(Result Position) | 맞는 결과가 목록에서 몇 번째에 있는지 |

학습에 사용한 실측 사례는 [`NH앱4개_카드검색_as-is결과.md`](./NH앱4개_카드검색_as-is결과.md)의 세 건이다.

```text
콕뱅크   K-패스카드 → 결과 0건            (결과가 없어서 실패)
올원뱅크 카드신청   → 결과 대량, 전부 무관 (결과는 있는데 관련도 실패)
NHPAY    카드 신청  → 정답 있음, 무관 혼재 (순위·정밀도 문제)
```

### 사용자가 직접 확인한 이해

- 올원뱅크 `카드신청`의 무관 결과 대량 노출을 검색어 매칭 문제가 아니라 관련도 문제로 분류했다. `신청` 글자로 데이터와 연결하는 데는 성공했으므로 매칭은 작동했고, 실패한 것은 연결된 것 중 무엇을 보여줄지 고르는 다음 단계라는 구분을 확인했다.
- NHPAY(부분)와 올원뱅크(완전 실패)를 다른 등급으로 보게 하는 차이를 "정답이 결과 목록 안에 있는지"로 판단했다. 무관 결과의 개수가 아니라 골라낼 정답의 존재가 등급을 가른다.
- 관련도가 0/1이 아니라 정도로 측정되며, NHPAY에 남은 문제는 결과 순위 수준이라는 것을 구분했다.
- 노출 조건을 `검색 결과 0건`만으로 잡으면 세 사례 중 가장 심한 올원뱅크형 실패가 기능 대상에서 빠진다고 판단했다. 현재 노출 조건에 "결과만으로 담당 채널·다음 행동이 불명확한 경우"가 함께 있는 이유를 확인했다.

관찰과 추정의 경계도 함께 확인했다. "글자만 매칭됐다"는 결과 화면에서 확인한 관찰이고, "올원뱅크는 카드 신청을 담당하지 않는다"는 화면만으로는 확정할 수 없는 추정이다. 아래 「가설 작성」에 기록된 혼동 지점이 바로 이 부분이다.

## 체화가 확인된 내용 4 — 과업 성공

과업 성공(Task Success)에서 실제로 정하는 것은 "성공했는지"가 아니라 "어디까지 가면 성공으로 볼 것인지" — 과업의 종료점이다. 종료점은 관찰에서 나오지 않고 PM이 정한다.

```text
앱들의 검색어 매칭·관련도를 고친다      ← 우리 범위 아님(NH 내부 개선)
올바른 앱·채널로 보낸다                 ← 사용자가 선언한 목표
그 앱 안에서 정확한 상품 화면까지 간다   ← MVP 제외(딥링크는 나중에 데이터만 추가)
신청을 완료한다                         ← 후행 가설, 직접 KPI 아님
```

### 사용자가 직접 확인한 이해

- 콕뱅크 크로스링크 사례(클릭 → 크롬 → NHPAY 웹 전체카드 79건)를 처음에는 클릭 발생을 근거로 성공으로 보았고, 클릭률(Click-Through Rate, CTR)은 검색 기능이 한 일이고 과업 성공은 사용자가 얻은 결과라는 구분으로 교정했다.
- 이 사례가 우리 기능이 아니라 NH의 현재(as-is) 동작이라는 것을 구분했다.
- 이어서 "일단 올바른 앱에 먼저 보내는 것이 목표"라고 스스로 종료점을 선언했다. 과업 성공의 정의가 관찰 결과가 아니라 결정 사항이라는 개념과 일치한다.

### 이 학습에서 나온 주 KPI 재검토 (결론: 현재 문구 유지)

종료점을 선언한 뒤, 주 KPI를 `외부 재검색이나 진행자 도움 없이 올바른 담당 채널과 다음 행동을 결정한 비율`에서 앱·채널 식별만으로 축소할지 검토했다. **검토 결과 판정 범위를 유지한다.** 축소안은 기각했다. 이후 2026-08-26에 문구에 `인앱검색만으로`를 넣는 정교화만 반영했고, 판정 범위는 그대로다. 근거는 [`decision-log/주KPI_문구정교화_확정.md`](./decision-log/주KPI_문구정교화_확정.md).

- 유지 근거: 안내를 노출하는 조건 자체가 "다음 행동이 불명확하다"이고([`B축_MVP_설계.md`](./B축_MVP_설계.md) 노출 조건 3번), 콕뱅크 79건 사례가 "앱은 맞게 갔으나 그 안에서 무엇을 할지 몰라 이탈한" 경우다. 판정에서 다음 행동을 빼면 기능이 해결하려는 문제를 판정이 보지 못한다.
- 목표(올바른 앱으로 보내기)보다 판정(역할·다음 행동까지 확인)을 엄하게 두는 것은 모순이 아니다. 판정을 엄하게 두면 합격한 사례를 확실한 성공이라고 말할 수 있다.
- 남은 위험: 표본 5~8명에서 조건 2개를 모두 요구하면 주 KPI 성공이 0~1건으로 깔릴 수 있다. 보조 지표 `올바른 채널 선택률`과 `올바른 다음 행동 설명률`을 반드시 함께 집계해 어느 조건에서 막혔는지 분리한다.
- 함께 검토했으나 채택하지 않은 안: 안내 카드 화면에서 다음 행동 표시를 빼는 안(기능 축소). 노출 조건 3번의 근거가 사라지고 [`decision-log/기능콘셉트_범용도구화_확정.md`](./decision-log/기능콘셉트_범용도구화_확정.md)의 확정 기능 정의와 충돌한다.

## 체화가 확인된 내용 5 — 검색 지표

지표 하나로 검색 품질을 관리할 수 없다. 지표마다 잡는 실패 유형이 다르기 때문이다. as-is 조사에서 관찰한 실패는 세 유형이다.

```text
A형  결과 0건                       콕뱅크 K-패스카드
B형  결과는 있으나 전부 무관         올원뱅크 카드신청, 스마트뱅킹 전반
C형  맞는 데까지 갔는데 뭘 할지 모름  콕뱅크 → 크롬 → 전체카드 79건
```

| 지표 | 계산 | 잡는 실패 | 놓치는 실패 |
|---|---|---|---|
| 검색 결과 없음 비율(Zero Results Rate, ZRR) | 0건으로 끝난 검색 ÷ 전체 검색 | A형 | B형 — 결과가 떠 있으면 0건이 아니다 |
| 재검색률(Query Reformulation Rate) | 검색어를 바꿔 다시 검색한 비율 | B형 | 어느 유형인지 구분 못 함(증상 지표) |
| 검색 결과 클릭률(Click-Through Rate, CTR) | 결과를 클릭한 검색 ÷ 전체 검색 | — | C형을 성공으로 집계 |

```text
결과 유무 ≠ 관련도
클릭 ≠ 과업 성공
채널 식별 ≠ 신청 완료
직접 KPI ≠ 후행 사업 성과
```

### 사용자가 직접 확인한 이해

- as-is 데이터로 흉내낸 ZRR 계산에서, NH스마트뱅킹은 확인된 검색 3건이 전부 실패했는데도 ZRR이 0%로 NHPAY와 같게 나온다는 것을 확인했다. 결과 화면에 무관한 것이라도 떠 있었기 때문이다.
- ZRR 하나만 KPI로 관리하면 부분 일치 범위를 넓혀 무관 결과라도 채우는 쪽으로 움직인다고 판단했다 — 굿하트의 법칙(Goodhart's Law).
- 다만 올원뱅크가 ZRR을 낮추려고 그렇게 했다는 것은 근거 없는 추정이고, `결과 대량 + 전부 무관`이라는 것만이 관찰이라는 구분을 확인했다.
- 재검색률에 해당하는 관찰 항목을 `검색어 재입력 횟수`와 `외부 검색 시도·시점·이유`로 짚었다.
- 증상 지표와 원인 지표를 구분했다. `외부 검색 시도율`은 A·B·C 어느 유형에서도 올라가므로 실패가 있었다는 것만 알려주고 무엇이 실패했는지는 구분하지 못한다.
- C형을 잡는 지표를 두 차례 다르게 골랐다가, 가상 참가자 P03의 관찰 기록표에서 실패로 찍히는 칸이 `참가자가 설명한 다음 행동` 하나임을 직접 읽어내며 교정했다. C형을 집계하는 보조 지표는 `올바른 다음 행동 설명률`과 `역할 오해율`이다.
- `올바른 채널 선택률`이 C형을 성공으로 집계한다는 점을 확인했다. 79건 목록 사례에서 사용자가 도착한 NHPAY는 맞는 채널이었다.

여기서 사용한 ZRR 수치는 검색어 4개 표본으로 흉내낸 계산이며 앱별 실제 ZRR이 아니다. 실제 ZRR은 서비스 검색 로그로만 계산할 수 있다.

### 주 KPI 유지 결정의 사후 확인

가상 참가자 P03(채널 정답, 역할 정답, 다음 행동 못 말함, 결정 35초, 재입력 0회, 외부 검색 없음)은 현재 주 KPI 기준으로 실패다. 만약 주 KPI를 앱·채널 식별로 축소했다면 이 참가자는 성공으로 집계됐다. 위 「이 학습에서 나온 주 KPI 재검토」에서 축소를 기각한 결정이 실제로 어떤 사례를 걸러내는지 보여주는 예다.

## 체화가 확인된 내용 6 — 가설 작성

가설 자체는 문제가 아니다. 문제는 가설을 관찰처럼 적어두는 것이다. 그러면 나중에 확인된 사실인지 내가 그렇게 생각한 것인지 구분되지 않는다.

```text
관찰  =  그 자리에 있던 다른 사람도 똑같이 확인할 수 있는 것
가설  =  관찰을 설명하려고 붙인 이유
```

반증 가능성(Falsifiability)은 `그 가설이 틀렸다면 무엇이 관찰될지`를 미리 적을 수 있는지를 뜻한다. 미리 적을 수 없으면 어떤 결과가 나와도 "역시 맞았다"로 끝난다.

### 사용자가 직접 확인한 이해

- as-is 문서에 직접 쓴 문장 세 개 중 관찰은 `올원뱅크 카드신청에서 무관 결과가 대량 노출된다` 하나뿐임을 짚었다. 나머지 둘(색인 품질 차이가 원인이라는 설명, 정밀도가 낮아 사용자가 이탈했을 것이라는 추정)은 확인할 수 없는 추론으로 분류했다.
- 같은 추론 안에서도 확인 가능한 것과 현재 방법으로 확인 불가한 것이 갈린다는 구분을 확인했다. 색인 가설은 비교 검색어(Control Query)로 확인할 수 있고, 이탈 원인 가설은 그 사용자의 당시 행동 기록이 없어 확인할 수 없다.
- `올원뱅크가 카드 상품 자체를 색인하지 않는다`는 가설의 반증 조건으로 `다른 실제 카드 상품명은 정확히 검색된다`를 골랐다. 메뉴로 들어갈 수 있다는 관찰은 `앱 안에 기능이 있음 ≠ 앱 검색 대상에 있음`이므로 반증이 아니고, 같은 실패가 반복되는 것은 지지 증거일 뿐 반증이 아니라는 것도 구분했다.
- **이 반증 조건은 실제로 확인됐다.** 2026-08-24에 스크린샷을 다시 보다가, NH스마트뱅킹에서 다른 실제 카드 상품명(`올바른이음카드`)으로 검색한 기록을 발견했고 결과는 상품 0건이었다. 반증되지 않았으므로 색인 가설이 지지된다. 상세와 한계는 [`NH앱4개_카드검색_as-is결과.md`](./NH앱4개_카드검색_as-is결과.md) 「비교 검색어(Control Query) 확인」.
- 프로젝트 가설(`담당 채널과 처리 경로를 안내하면 외부 재검색·도움 없이 올바른 채널과 다음 행동을 결정할 수 있다`)의 반증 조건으로 `안내를 보고도 외부 검색을 하거나 다음 행동을 못 말한다`를 골랐다. Before의 포털 우선 행동은 문제 존재의 근거이지 해결안 가설의 반증이 아니고, 표현이 어렵다는 반응은 실패의 이유일 수 있으나 반증 자체는 아니라는 구분을 확인했다.

### 반증 조건에서 외부 검색을 뺐다 (2026-08-26)

발표 자료를 만들다가 위 반증 조건의 `외부 검색을 하거나` 부분이 확정 사항과 어긋난다는 것을 사용자가 짚었다.

```text
문제   외부 검색으로 신청하는 것도 사용자 입장에선 올바른 채널이다
       그걸 반증 조건으로 세우면 문제를 해결한 사람까지 실패로 센다
```

두 가지가 섞여 있었다.

1. **관점이 섞였다.** 포털로 70초 만에 신청한 것은 사용자 관점에선 성공이고 회사 관점에선 통제 상실이다. 사용자 관점으로 쓴 가설에 회사 관점의 실패를 붙여둔 상태였다.
2. **외부 검색이 두 종류인데 갈리지 않는다.** 안내를 못 믿어 확인하러 나가는 것은 안내 실패의 신호지만, 그저 포털이 편해서 쓰는 것은 아니다. 진행자가 이유를 묻지 않으면 구분되지 않는다.

이 지적은 이미 확정된 입장과 같다 — [`decision-log/포털대체와_공식판별_확정.md`](./decision-log/포털대체와_공식판별_확정.md)의 **「포털 사용 자체를 실패로 보지 않는다」**(2026-08-22 확정). 진행안의 「별도 기록」에도 `외부 검색 후 정답`은 실패가 아니라 별도 기록으로 들어있었다. **반증 조건 문장만 늦게 따라간 것이다.**

따라서 반증 조건을 안내의 기능 실패만 남기도록 좁혔다.

```text
이전   안내를 보고도 외부 검색을 하거나 채널을 고르지 못한다
이후   안내를 보고도 담당 채널을 짚지 못하거나 틀린 채널을 고른다
```

외부 검색을 안 보게 된 것이 아니다. **주 KPI의 조건(`외부 재검색이나 도움 없이`)과 보조 지표(`외부 검색 시도율`)에 그대로 남아 있다.** 바뀐 것은 그것만으로 **가설 전체를 폐기하지는 않는다**는 점이다.

여기서 얻은 구분은 다음과 같다.

| | 역할 | 성격 |
|---|---|---|
| 주 KPI | 얼마나 잘 됐는지 재는 눈금 | 연속적 |
| 반증 조건 | 가설을 폐기할지 선언하는 선 | 이분법 |

같은 문장이라도 **조건일 때와 판정일 때가 다르다.** 반증 조건은 가설을 버릴 기준이므로 **논쟁 여지가 없는 실패만** 담아야 하고, 애매한 것을 넣으면 멀쩡한 가설이 잘못 폐기된다.

좁힌 문장은 빼기만 한 것이 아니다. 옛 문장은 `채널을 고르지 못한다`만 잡아 **틀리게 고른 참가자를 통과시키는 구멍**이 있었다. 새 문장은 `틀린 채널을 고른다`를 넣어 그 구멍도 메웠다.

### 반증 조건 후보를 늘릴지 검토했다 (2026-08-26)

반증 조건은 **층위가 다르다**는 것을 구분했다 — 기능(안내가 채널을 알려주는가) / 효과(안내가 없을 때보다 나은가) / 신뢰(알려줘도 받아들이는가). 다섯 후보를 놓고 비교한 뒤 **기능 하나만 유지하기로 했다.**

| 후보 | 잡는 것 | 판단 |
|---|---|---|
| 기능 — 담당 채널을 짚지 못하거나 틀린 채널을 고른다 | 안내 자체의 실패 | **채택** |
| 효과 — 안내 없는 조건의 성공 ≥ 있는 조건 | `안내하면`이라는 인과 주장 | 사용성테스트 진행안에 이미 있어 중복. Before가 자유 탐색이라 엄밀한 대조군도 아니다 |
| 신뢰 — 공식인지 판별하지 못하거나 믿지 못한다 | 정보는 맞는데 안 받아들이는 실패 | P02가 실제 사례지만 이번엔 보류 |
| 주목 — 안내 카드를 읽지 않고 지나친다 | 노출됐는데 안 보이는 실패 | 기각. 가설의 반증이 아니라 **배치·디자인 문제**다. 안 봤으면 검증이 안 된 것이지 틀린 것이 아니다 |
| 행동 — 채널은 맞췄는데 다음 행동을 못 말한다 | 채널만 알고 못 쓰는 경우 | **조건 ①에 흡수.** 안내 한 줄은 `어느 채널`과 `거기서 무엇을` 둘을 말하므로, 하나라도 전달되지 않으면 같은 실패다 |
| 비용 — 결정 시간이 Before보다 길다 | 맞긴 한데 더 나쁜 경우 | 기각. 3~5명에서 시간 중앙값은 한 명이 헤매면 통째로 흔들린다 |

하나로 좁힌 이유는 **반증 조건이 여러 개면 OR**이기 때문이다. 하나만 걸려도 가설을 폐기하므로 늘릴수록 가설이 쉽게 죽는다.

### 실패 지점을 셋으로 나눠 반증 조건을 하나 더 넣었다 (2026-08-26)

사용자가 `안내한 채널에서도 찾지 못한다`를 반증 조건으로 세워야 하지 않느냐고 물었다. 검토하면서 실패 지점이 하나가 아니라는 것이 드러났다.

| | 실패 | 책임 |
|---|---|---|
| ① | 안내를 봤는데 어느 채널인지 못 짚거나, 짚었어도 거기서 무엇을 할지 말하지 못한다 | 안내의 전달 |
| ② | 안내가 가리킨 채널이 애초에 틀렸다 | **라우터 자신** |
| ③ | 맞는 채널에 갔는데 거기서 못 찾는다 | 그 앱 |

기존 반증 조건은 ①만 담고 있었다. **②가 빠져 있다는 것이 이 검토에서 드러났다** — 라우터가 잘못된 채널을 안내하면 사용자는 시키는 대로 따랐으므로 `틀린 채널을 고른다`에 걸리지 않는다. 라우터의 실패인데 반증에 안 걸리는 상태였다. 그래서 ②를 추가했다.

```text
반증 조건 1   안내를 보고도 담당 채널을 짚지 못하거나,
             짚었어도 거기서 무엇을 할지 말하지 못한다
반증 조건 2   안내한 채널이 실제 담당이 아니다
```

③은 넣지 않았다. 두 가지 이유다.

- **통제 밖이다.** 라우터는 `이 목적이면 이 앱`까지만 책임진다. 그 앱 안의 검색과 화면은 그 앱 팀의 것이다. 안내 한 줄이 책임지는 범위가 `어느 채널 + 거기서 무엇을`까지이고, **목표와 판정이 모두 거기까지다.** 그 채널에 도착한 뒤 실제로 해내는지는 그 범위 밖이다.
- **지금 프로토타입으로 못 잰다.** `올원뱅크목업_안내형_프로토타입.html`은 채널을 누르면 결정 화면으로 넘어갈 뿐 목적지 앱을 재현하지 않는다. 도착 이후를 관찰할 화면 자체가 없다.

다만 ③은 **실제로 관찰된 문제**다. 콕뱅크에서 `카드 신청`을 누르면 NH Pay 웹의 전체 카드 79건 목록에 떨어진다. 반증이 아니라 **한계·가드레일**로 다룬다.

### 이 학습에서 드러난 공백 (미해결)

프로젝트 가설에 반증 조건을 대보니 **판정 기준선이 없다**는 것이 드러났다. 진행안에는 1차 KPI 산식만 있고 `얼마 이하면 가설이 틀렸다고 볼지`가 어디에도 없다. After 테스트의 표본 규모도 명시돼 있지 않다.

2026-08-24에 `유효 참가자 3~5명 + 바닥 조건(0명 반증 / 과반 이상 지지 / 그 사이 보류)` 안을 문서화했으나 사용자 판단으로 되돌렸다. **따라서 판정 기준은 여전히 미정이다.** 다만 아래 논의는 끝났으므로 처음부터 다시 검토하지 않는다.

- 3~5명에서 한 명은 20~33%p이므로 비율 기준선 하나로 지지·반증을 가르면 참가자 한 명이 결론을 뒤집는다.
- 이 규모는 모집단 비율 추정용이 아니라 문제 발견용이다.
- 기준선을 하나만 두면 애매한 결과를 유리하게 해석하게 되므로 보류 구간을 미리 두는 방식을 검토했다.
- 판정 기준을 테스트 전에 적어두는 것 자체가 과제 평가 항목 `재현성`의 근거가 된다.

단계 전환 조건 네 가지(검색 대상·검색어 매칭·검색 관련도·과업 성공)와 이후 남았던 검색 지표·가설 작성까지 2026-08-24로 모두 확인됐다.

**사용자가 "다음 단계로 넘어가자"고 결정하기 전에는 NH 앱 비교용 분석 프레임워크를 작성하지 않는다.** 학습이 끝났다는 것이 곧 다음 단계 착수 승인은 아니다.
