# 담당 채널 안내 프로토타입 사용성 테스트 진행안

- 최종 수정일: 2026-08-22
- 문서 유형: 계속 갱신
- 대상: 최근 은행 앱 사용 경험이 있는 참가자
- 예상 시간: 1명당 10분 내외

> 파일명에는 과거 분류인 `B축`이 남아 있다. 기존 배포 프로토타입은 공통 목적지 자동 이동형이므로 현재 안내형 해결안의 After 테스트에 그대로 쓰지 않는다. [`B축_MVP_설계.md`](./B축_MVP_설계.md)에 맞춘 버전이 준비된 뒤 이 절차를 사용한다.

## 목적

검색 결과에 기능별 담당 채널과 역할을 안내하면 사용자가 외부 재검색이나 진행자 도움 없이 인앱검색만으로 **올바른 채널과 다음 행동을 결정할 수 있는지** 확인한다.

자유 탐색 Before는 [`K패스카드_과제수행테스트_진행안.md`](./K패스카드_과제수행테스트_진행안.md)에 따라 별도로 수집한다. Before와 After는 환경이 다르므로 동일 조건의 전후 실험처럼 직접 개선율을 계산하지 않는다.

## 검증 질문

1. 참가자는 안내를 보고 K-패스카드 처리가 가능한 채널을 고를 수 있는가?
2. 선택한 채널에서 무엇을 해야 하는지 설명할 수 있는가?
3. `완료·경유·안내` 역할을 구분하는가?
4. 복수 채널이 제시되어도 합리적인 선택을 하는가?
5. 안내만으로 부족해 외부 검색이나 진행자 도움을 요청하는가?

## 참가자 조건

- 최근 6개월 안에 모바일 은행 앱을 사용한 사람
- NH 앱 사용자일 필요는 없음
- 특정 카드 발급 경험은 필수 아님
- 금융사·핀테크 종사자는 별도 표시해 해석 시 구분

## 준비물

- **실제 구현으로 테스트한다.** 별도 설문이나 이미지가 아니라 동작하는 화면을 쓴다.
  - `prototype/router/bank-app.html` — 계열사 앱 시뮬레이터. 4개 앱 as-is 재현 · 안내 노출 · 리소스 계측
  - `prototype/router/console.html` — 라우터 콘솔. 등록 → 승인 → 발행 → 되돌리기
  - `prototype/자유탐색_폰목업.html` — 폰 홈에서 4개 앱과 인터넷 검색을 오가는 자유 탐색용. 포털은 2026-08-25 네이버 실측 캡처를 쓴다
  - 실측이 없는 화면은 지어내지 않고 `준비되지 않음`으로 끝낸다. **무엇을 누르려 했는지가 기록에 남으므로 그 자체가 자료가 된다**
- 참가자 본인 또는 테스트용 스마트폰
- 관찰 기록표
- 화면·음성 기록 동의 문구(기록할 경우)

## 진행 원칙

- 참가자에게 정답 앱, 검색어, 채널 수를 미리 알려주지 않는다.
- 화면 조작법에 필요한 최소 안내만 한다.
- 막혀도 즉시 도와주지 않고 도움 요청 여부와 시점을 기록한다.
- 외부 검색을 시도하면 막지 않고 이유를 묻는다.
- ‘신청 완료’가 아니라 ‘담당 채널과 다음 행동 결정’에서 과제를 종료한다.

## 시작 안내문

> 지금부터 금융 앱 검색 화면을 이용해 특정 기능을 어디에서 처리할 수 있는지 찾아보겠습니다. 여러분을 평가하는 것이 아니라 화면의 안내가 이해되는지 확인하는 테스트입니다. 평소처럼 자유롭게 사용해 주세요. 필요하다고 생각하면 다른 방법을 사용하셔도 됩니다.

## 과제

> 대중교통비 환급 혜택을 받을 수 있는 K-패스카드를 발급받으려 합니다. 이 화면을 이용해 어느 채널에서 무엇을 해야 하는지 결정한 뒤 말씀해 주세요.

## 진행 순서

1. 안내형 프로토타입 첫 화면을 보여주고 타이머를 시작한다.
2. 참가자가 자유롭게 검색하고 결과를 읽게 한다.
3. 참가자가 채널과 다음 행동을 결정하면 그렇게 생각한 근거를 묻는다.
4. 5분이 지나거나 참가자가 포기하면 종료한다.
5. 정답 판정 후 짧은 사후 질문을 진행한다.

## 성공 판정

### 1차 성공

다음 조건을 모두 충족하면 성공으로 기록한다.

- 외부 재검색이나 진행자 도움 없이 처리 가능한 채널을 선택한다.
- 해당 채널의 역할과 다음 행동을 맞게 설명한다.

복수의 `완료` 채널이 존재하면 그중 하나를 선택해도 성공이다. `안내` 채널을 최종 처리 채널로 오해하거나, 안내 화면을 신청 완료로 이해하면 실패 또는 오인 성공으로 기록한다.

**다음 행동의 판정선** — 사람마다 갈릴 수 있어 예시로 못박는다.

```text
성공   "NH Pay 앱에서 카드 목록을 열고 K-패스카드를 찾아 신청한다"
성공   "NH농협카드 모바일웹에 들어가 카드 신청 메뉴로 간다"
실패   "신청한다"            화면 문구를 옮긴 수준
실패   "거기서 하면 된다"      행동이 없음
```

근거를 물었을 때 `카드에 그렇게 써 있어서`뿐이면 **읽기만 한 것**으로 보고 성공으로 세지 않는다. `올원뱅크는 안내만 한다고 돼 있어서`처럼 역할을 읽어낸 답이어야 한다.

### 별도 기록

- 외부 검색 후 정답: 과제 결과는 별도로 기록하되 1차 KPI 성공에는 포함하지 않음
- 진행자 도움 후 정답: 도움 성공으로 분리
- 포기 또는 제한 시간 초과: 실패
- 잘못된 채널을 확신: 오인 성공

### 반증 조건

**재기 전에 정한다.** 재고 나서 정하면 결과에 맞춰 기준이 움직인다.

```text
안내 없는 조건의 성공 ≥ 안내 있는 조건의 성공
  → 안내가 도움이 된다는 근거를 얻지 못한 것으로 본다
```

표본이 작으므로 **비율로 쓰지 않고** `6명 중 4명`처럼 센다. 참가자별 사례로 서술하고, 자유 응답은 요약하지 않고 원문을 남긴다.

## 종료 후 질문

1. 어떤 정보를 보고 채널을 골랐나요?

3. 채널이 여러 개라 선택하기 어려웠나요? 무엇이 더 필요했나요?
4. 화면을 본 뒤에도 외부 검색이 필요하다고 느꼈나요? 왜 그런가요?

## 계산할 지표

### 1차 KPI

`무도움 올바른 결정률 = 외부 검색·진행자 도움 없이 인앱검색만으로 올바른 채널과 다음 행동을 결정한 사람 ÷ 유효 참가자 수`

### 보조 지표

- 올바른 채널 선택률
- 올바른 다음 행동 설명률
- 결정 시간 중앙값
- 외부 검색 시도율
- 도움 요청률
- 역할 오해율
- 복수 채널로 인한 결정 보류율

## Before 자료와 함께 해석하는 법

- Before에서는 포털 선시작, 앱 시작 후 포털 이탈, 전체 외부 검색 의존을 행동 지표로 본다.
- After에서는 안내를 받은 뒤 무도움으로 올바른 결정을 내리는지를 본다.
- 두 결과는 `문제 행동이 존재하는가`와 `안내가 의사결정을 돕는가`를 각각 뒷받침한다.
- 모집 조건, 매체, 과제 종료점이 같지 않으면 수치를 빼서 개선율로 표현하지 않는다.

## 한계

- 웹 프로토타입은 실제 앱 전환·로그인·설치·신청 마찰을 반영하지 못한다.
- 소규모 편의 표본은 통계적 대표성을 갖지 않는다.
- K-패스카드 한 과제의 결과만으로 다른 저빈도 금융 기능까지 일반화할 수 없다.
- 참가자가 테스트 의도를 추측해 안내를 평소보다 자세히 읽을 수 있다.
- 올바른 채널 결정이 실제 신청 전환으로 이어지는지는 별도 행동 데이터가 필요하다.
