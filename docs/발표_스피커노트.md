# 발표 스피커 노트

- 문서 유형: 계속 갱신
- 목적: 슬라이드(`prototype/slides/`)는 핵심 한 줄+숫자만 남기고, 근거·세부설명·조심할 것은 이 문서에 둔다. 발표자가 화면을 보며 말로 채우는 용도다.
- 단일 기준 관계: 흐름은 [`발표 흐름.md`](./발표%20흐름.md), 사실 근거는 각 절에 링크된 원본 문서.

## 표지 — 채널 안내 기능

말할 것: "기업의 서비스를 안내하는 기능"이라는 한 줄 태그라인 그대로 소개.

## 01 가설과 반증 (2장)

**화면 1 — 가설**
- 화면 표시: "사용자는 이름은 아는 상품을 어느 앱에서 처리하는지 알지 못한다" + 큰 숫자 "15명 중 1명"
- 말할 것: 앱을 먼저 여는 15명 중 담당 앱(NH Pay)을 고른 사람은 1명뿐이다. 같은 15명 중 7명은 담당 앱이 아닌 것을 고르고도 확신도 4~5를 줬다. 올원뱅크에서 "카드신청" 검색 시 39건이 나오는데 전부 퇴직연금 관련이라 무관하다.
- 화면: as-is 검색 결과 캡처 한 장 (39건인데 전부 무관한 게 눈으로 보이는 것)
- 근거: 인식설문 25건, `NH앱4개_카드검색_as-is결과.md`

**화면 2 — 왜 나뉘어져 있는가**
- 화면 표시: "법인도, 검색 방식도 다 다르다" + 관리주체 다름 / 인앱검색 방식 다름 두 태그
- 말할 것: 농협금융지주는 은행 계열 앱 7개를 스마트뱅킹·기업스마트뱅킹·올원뱅크 3개로 이미 통합했다. 콕뱅크(상호금융)·NHPAY(카드)는 원래 다른 법인·다른 사업이라 이 통합 대상 자체가 아니었다. 콕뱅크와 올원뱅크·스마트뱅킹은 감독 체계가 다른 별도 법인이고, 앱마다 검색 로직·색인이 전부 달라 같은 검색어에도 결과가 다르게 나온다.
- 근거: `NH앱4개_카드검색_as-is결과.md` 「NH 앱 분리의 조직적 배경」

## 02 포털이 이미 대체하고 있다

- 화면 표시: "60%가 포털로 간다" + 구글폼 시각화 자료
- 말할 것: 실패하면 포털로 가겠다는 사람이 15명 중 9명(60%)이다. 거대한 기능일수록 개발 리소스 대비 필요성이 희미해진다 — 이미 포털이 대체하고 있기 때문이다.
- 조심할 것: `40%`(처음부터 포털)와 `60%`(실패하면 포털)는 다른 문항이다. 섞지 않는다.
- 근거: `raw/260825 NH앱 담당경로 인식설문 응답.csv`

## 03 그렇다면 만들면 안될까?

말할 것: 뜸을 들이는 전환 슬라이드. "이미 대체되고 있는데도, 만들어야 할 이유가 두 가지 남아 있습니다."

## 04 만들어야 할 이유① — 농협중앙회 관점

- 화면 표시: "포털로 나가는 손해는 그룹 전체가 진다" + "이미 있는 조직 위에 얹는 일"
- 말할 것: 은행은 은행 실적, 상호금융은 조합 실적만 본다. 이 손실을 그룹 전체로 내부화해서 느끼는 유일한 주체가 중앙회다. "상호금융부문"처럼 각 조합·계열사를 지도·검사하는 조직이 이미 있어서, 크로스앱 매핑 승인 같은 기능은 완전히 새로 만드는 게 아니라 기존 조직 위에 얹는 일이다.
- 질문 나오면: 지배구조는 농협중앙회 → 지분 100% → 농협금융지주 → 지분 100% → 농협은행이다. 중앙회 회장은 계열사 대표 인사권·예산권·감사권도 갖는다 — 승인을 실제로 강제할 수 있는 위치다.
- 근거: 한경매거진&북 「700조 자산의 조직 농협은 어떻게 구성됐나」 외 (2026-08-25 웹 조사)

## 05 만들어야 할 이유② — 다른 은행으로 빠져나갈 수 있다

- 화면 표시: "카드사 필터 7건 중 일곱 번째" + 네이버 캡처
- 말할 것: 네이버에서 `k-패스카드`를 검색하면 최상단은 모두의카드(정부 정책 채널, K-패스 공식 발급 창구)이고, 그 아래 신용카드 관련광고 7건 중 1위는 KB국민이다. NH농협카드는 그 카드사 필터 7건 중 일곱 번째, 맨 끝에 있다.
- 파일럿 관찰(P02): 모두의카드에서 약 1분 헤매다 답을 못 얻고 이탈 → 재검색 → 신용카드 비교·광고 지면을 거쳐 신한으로 결정했다. 공식 채널(모두의카드)에 도달했는데도 그게 공식인지 몰라서 쓰지 않았다.
- 결론: 회사는 이 지점부터 포털사이트에 기생하는 구조가 된다.
- 근거: `decision-log/포털대체와_공식판별_확정.md`, `K패스카드_과제수행테스트_진행안.md`

## 06 해결안 + 구조

- 화면 표시: "검색어 → 담당 채널 + 역할 + 다음 행동" + 4줄 / 0 B / 304·수신0B / 2칸
- 말할 것: 검색 결과를 바꾸지 않는다. 그 위에 안내만 얹는다. 담당 채널은 검색 데이터가 아니라 조직 데이터다. 구조는 지능은 중앙, 앱은 조회만 — 앱 호출부 4줄, 검색당 네트워크 0 B, 변경 없을 때 304·수신 0 B, 계열사가 손으로 채우는 칸은 2개뿐이다.
- 조심할 것: 자동으로 이동시키지 않는다(2026-08-22 확정). 질문 나오면 딥링크 백엔드는 범위 밖이라고 답한다.
- 근거: `prototype/router/README.md`

## 07 지표

- 화면 표시: 1차 KPI 문장 + "15명 중 7명"(가드레일)
- 말할 것: 1차 KPI는 "외부 재검색이나 진행자 도움 없이 올바른 담당 채널과 다음 행동을 결정한 참가자 비율"이다. 채널만 맞혀도 다음 행동을 모르면 여전히 실패라서 둘 다 본다. 보조 지표는 6개(채널 선택률, 다음 행동 설명률, 결정 시간, 재입력 횟수, 외부 검색 비율, 역할 오해율) — 전부 검증 예정이다. 가드레일 "잘못된 채널을 확신하는 비율"만 Before 값이 있다: 앱을 먼저 여는 15명 중 7명이 오답을 확신도 4~5로 답했다.
- 방법상 한계: 통제된 과제에서 보기를 주고 재면 회상이 재인으로 바뀌어 실제보다 높게 나올 수 있다. 배포 후에는 「안내 노출 후 재검색률」을 주지표로 별도로 잰다.
- 근거: `B축_MVP_설계.md` 「검증 기준」

## 08 시연

- 화면 표시: 4단계 (검색 0건 → 등록·승인·발행 → 동기화 200 OK → 재동기화 304)
- 말할 것: 승인을 건너뛰면 빈 기준이 나가서, 앱은 200 OK를 받고도 아무 안내를 못 띄운다. 시연하다 그걸 겪고 이 관문을 막았다.
- 준비: `router/console.html`, `router/bank-app.html`(발표 모드 버튼)

## 09 기대효과

- 화면 표시: `PROJECT_GUIDE.md` 목표 4개(3개는 검증 목표, 1개는 후행 가설로 분리)
- 말할 것: 은행 앱 사용자가 저빈도 금융 기능을 찾을 때 선택하는 자연스러운 탐색 경로와 외부 검색 의존을 확인하고, 검색 실패로 발생하는 불필요한 외부 재검색과 담당 채널 오인을 측정하며, 담당 채널 안내가 외부 재검색 없이 올바른 채널과 다음 행동을 결정하게 하는지 프로토타입으로 검증한다. 실제 신청 전환율 개선은 후행 사업 가설로 분리한다.

## 10 한계와 확장 지표

- 화면 표시: "사용자 효과는 재지 못했다" / "NH 사례 하나뿐" + "배포 후엔 재검색률로 잰다"
- 말할 것: 참가자를 모으지 못해 이번 마감 범위에서 제외했다. 판정 기준과 진행 절차는 다 만들어져 있다. 일반화 근거도 NH 사례 하나뿐이라 다른 회사·업종은 확인하지 못했다. 대신 시연하다 찾아 고친 결함 여섯 개와 자동 검사 104건(화면이 아니라 실제 코드, 남이 받아서 돌릴 수 있음)을 확인했다. 배포 후 주지표는 "안내 노출 후 재검색률"이고, 앱마다 스냅샷 받는 시점을 달리해 자연 비교군을 만든다.
- 검증 설계 자체의 한계: 통제된 과제에서 보기를 주고 재면 실제보다 높게 나온다.
- 근거: `B축_MVP_설계.md` 「운영 단계 지표」
