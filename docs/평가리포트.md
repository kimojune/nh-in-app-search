# 평가 리포트 — NH 인앱검색 담당 채널 안내

- 작성일: 2026-08-26
- 상태: 초안 (에이전트 작성. 발표 후 A01·A02 원자료를 반영해 갱신한다)
- 문서 유형: 제출물

## 한 줄

검색 결과가 나쁜 것이 문제가 아니라 **어느 앱이 담당인지 아무도 알려주지 않는 것**이 문제였고, 그 안내를 **계열사 앱이 거의 부담하지 않는 방식**으로 얹을 수 있다는 것까지 만들어서 확인했다. **사용자 효과는 아직 재지 못했다.**

## 지표

**지금 제시할 수 있는 것은 문제의 크기와 도입 비용이며, 사용자 효과가 아니다.** 이 구분을 먼저 밝힌다.

### 문제의 크기

```text
앱을 먼저 여는 15명 중 담당 앱(NH Pay)을 고른 사람        1명
같은 15명 중 담당 앱이 아닌 것을 고르고 확신도 4~5         7명
못 찾으면 포털로 간다고 답한 사람 (25명 중)               15명
올원뱅크 "카드 신청" 검색 결과                            39건 — 법원등기 · 퇴직연금
```

출처: 인식 설문 25건, `docs/NH앱4개_카드검색_as-is결과.md`

### 도입 비용 (측정값)

```text
명부를 가져오는 코드                     4줄
검색 한 번이 쓰는 네트워크                0 B
하루 1회 확인 — 안 바뀌면                 0 B
          바뀌면 (기능 2,000건 기준)      약 340 KB
계열사가 손으로 채우는 칸                 2개 (채널 역할 · 다음 행동)
조회 1회 (명부 크기와 무관)               0.0002 ms
```

출처: `prototype/router/README.md` 「측정값」, `tests.mjs`

### 아직 재지 못한 것

```text
안내 노출 후 재검색률           배포 후에만 잰다
담당 채널 선택률               실험군 2명 · 대조군 없음
결정 시간                     순수 탐색시간이 P01·P02 모두 미측정
```

## 개선 전후 — 왜 단일 개선율을 계산하지 않았나

**과제가 요구하는 `개선 전후`를 하나의 개선율로 내지 않았다.** 숨긴 것이 아니라 계산하면 거짓말이 되기 때문이다.

Before는 **포털까지 열어둔 자유 탐색**이었다. 은행·카드사·앱·포털을 지정하지 않았고, 참가자가 네이버를 켜든 앱을 열든 막지 않았다. 그렇게 설계한 이유는 **`막히면 밖으로 나간다`는 행동 자체를 재려는 것**이었다.

After에서 같은 조건을 주려면 프로토타입 안에서도 포털로 나갈 수 있어야 한다. 여기서 갈라진다.

```text
나갈 수 있게 두면   나가는 순간 관찰이 끊긴다
못 나가게 막으면    Before가 재던 행동 자체가 사라진다
```

**조건을 맞추면 재려던 것이 없어지고, 맞추지 않으면 비교가 안 된다.** 두 조건의 환경과 종료점이 다른 채로 개선율을 내면, 그 숫자는 안내의 효과가 아니라 **조건 차이**를 말하게 된다.

그래서 실험실 비교를 포기하고 **배포 후 실사용 로그로 비교하는 설계**로 바꿨다.

| | 방법 | 이미 만들어둔 재료 |
|---|---|---|
| 비교군 | 앱마다 스냅샷 반영 시점을 달리해 **자연 비교군**을 만든다 | 스냅샷 버전 · ETag |
| 대상자 | **0건 로그**로 같은 상황의 사용자를 추린다 | 콘솔 「로그로 후보 찾기」 |
| 주 지표 | 안내 노출 후 **재검색률** | `B축_MVP_설계.md` 「운영 단계 지표」 |

이번 마감에는 그 설계를 실행할 시간이 없어 구현을 우선했다. **못 한 것은 실행이지 설계가 아니다.**

상세는 [`decision-log/After검증_실사용로그전환_제안.md`](./decision-log/After검증_실사용로그전환_제안.md).

## 실패 원인 분석

같은 검색어인데 앱마다 **실패하는 이유가 달랐다.** 배운 언어로 나눠 보니 종류가 갈렸다.

| 앱 | 결과 | 실패 종류 |
|---|---|---|
| NH콕뱅크 | 0건 · 엉뚱한 추천검색어 | **검색 대상에 없음** |
| NH올원뱅크 | 39건 — 법원등기 · 퇴직연금 | **관련도 실패** |
| NH스마트뱅킹 | 보안카드 · OTP 메뉴만 · 상품 0건 | **관련도 실패** |
| NH Pay | K-패스카드(신용/체크) 정확히 매칭 | 성공 — 그런데 |

NH Pay가 맞은 것은 검색이 뛰어나서가 아니라 **카드가 원래 그 앱 데이터라 우연히 들어 있었기 때문**이다. 즉 **데이터가 우연히 있는 곳만 맞는다.**

### 근본 원인은 조직 경계다

```text
농협중앙회        상호금융 · 콕뱅크
NH농협금융지주    농협은행 → 올원뱅크 · 스마트뱅킹
                 은행 안에서도 카드 사업부문이 달라 NH Pay가 따로
```

2012년 신경분리로 금융은 지주로 가고 상호금융만 중앙회에 남았다. **경계가 두 겹**이라 앱이 나뉘어 있다. 담당 채널은 **검색 데이터가 아니라 조직 데이터**이므로, 각 앱의 검색 품질을 올려도 해결되지 않는다.

### 지표가 이 실패를 놓친다

```text
콕뱅크        결과 0건               ZRR 50%
스마트뱅킹     확인한 3건 전부 실패     ZRR 0%
올원뱅크       39건 전부 무관          ZRR 0%
NH Pay       정확히 매칭             ZRR 0%
```

**ZRR만 보면 실패한 앱이 성공한 앱과 똑같아 보인다.** 이 지표만 관리하면 결과를 아무거나 채우는 쪽으로 움직인다 — 굿하트의 법칙. 그래서 종료점을 **`담당 채널을 스스로 찾아냈는가`** 로 옮겼다.

## 만든 것

**지능은 중앙에, 말단은 사전 조회만.**

```text
[콘솔]                    [스냅샷]                [계열사 앱]
등록 · 검토 · 승인 · 발행   →  routing-index.json  →  조회 함수 하나
정규화 · 표현 확장 ·           버전 + ETag             네트워크 0 · 판단 로직 없음
노출 억제 판단까지 중앙에서
```

- **검색을 고치지 않는다.** 검색 결과 위에 안내만 더한다.
- **화면은 앱이 그린다.** 데이터만 주고 안내 카드는 앱의 디자인으로 붙인다. 남의 UI를 넣지 않는 것이 도입 조건이었다.
- 계열사는 **이미 가진 데이터를 내보내 올린다.** 구분자·컬럼명이 서로 달라도 흡수한다(쉼표 · 탭 · 파이프 · 세미콜론, 영문 약어 컬럼은 수동 매핑).
- 손으로 채우는 값은 **채널 역할과 다음 행동 둘뿐**이다.

## 설계에서 맞바꾼 것

| 택했다 | 대신 포기한 것 | 왜 |
|---|---|---|
| 지능을 중앙에 둔다 | 중앙이 틀리면 네 앱이 한꺼번에 틀린다 | 앱마다 판단이 갈리지 않는다. 그래서 「안내한 채널이 실제 담당이 아니다」를 반증 조건에 넣었다 |
| 안내만 하고 보내지 않는다 | 사용자가 한 번 더 움직여야 한다 | 딥링크는 앱마다 별도 합의가 필요하다. 협의 없이 붙는 것이 도입 조건이었다 |
| 검색어를 밖으로 보내지 않는다 | 라우터가 사용자 행동을 전혀 보지 못한다. 그룹 안 이동률도 못 잰다 | 검색할 때 네트워크가 0이라 **제3자 제공 동의가 필요 없다**. 측정하려고 계열사끼리 사용자를 식별해 맞추면 **도입 장벽을 도로 올린다** |
| 하루 1회 묻고, 바뀌었을 때만 받는다 | 반영이 하루 늦고, 명부가 커지면 전송량이 는다 | 늘어난 전송량은 무관한 결과와 기존 크로스링크를 걷어내면 상쇄될 여지가 있다 — 검토 대상 |
| 데이터만 주고 화면은 앱이 그린다 | 앱에 렌더링 작업이 생긴다 | 남의 UI가 들어가면 디자인 시스템 · 접근성 · 심사에서 막힌다 |
| 통합을 기다리지 않고 다리를 놓는다 | 슈퍼앱 전환이 끝나면 역할이 사라진다 | 통합은 몇 년이 걸린다. 그 사이에도 사용자는 매일 헤맨다 |

**다섯 번 다 `계열사 앱이 부담을 지지 않는다`를 우선했다.** 운영 주체가 다른 앱들이라, 도입 비용이 크면 채택 자체가 안 되기 때문이다.

## 한계

```text
[표본]
  K-패스카드 한 사례다 — 저빈도 금융 기능 전체로 넓힐 수 없다
  as-is는 본인이 직접 검색한 n=1 기록이고, 비교 검색어 확인도 스마트뱅킹 1건뿐이다
  설문 25건 · 실험군 2명 · 대조군 없음
  P01 · P02 모두 앱 진입·로그인 대기가 따로 측정되지 않아 순수 탐색시간이 미확인이다

[검증 설계]
  안내가 실제로 사용자를 돕는지 확인하지 못했다
  주 KPI에 두 관점이 섞여 있다 — 외부 검색으로 해결한 경우는 회사 관점의 이탈이지만
    사용자 관점에서는 성공이다. 한 숫자가 두 관점을 동시에 말한다.
    둘을 가르려면 기업 내부 데이터가 있어야 한다 (앱 밖은 보지 못한다)
  After 테스트의 판정 기준선(얼마 이하면 틀렸다고 볼지)이 미정이다
  자연 비교군은 무작위 배정이 아니라 검색어군을 맞춰 보정해야 한다

[구현]
  명부 서명 검증이 없다 — 변조되면 그대로 피싱 화면이 된다. 실서비스에서는 필수다
  0건 로그를 앱에서 모아 내보내는 쪽은 구현하지 않았다
  콘솔 쪽(CSV 파서 · 로그 후보) 자동 검사가 분리돼 있지 않아 수동 절차로만 확인했다
  서버가 없어 여러 기기 · 여러 사람 간 공유가 되지 않는다
  권한 분리와 반려는 미구현이다

[NH 실제 환경]
  실제 검색 인덱스 · 조직 권한 · 운영 비용을 확인하지 못했다
  웹 프로토타입은 실제 앱의 로그인 · 보안 · 로딩 · 딥링크 마찰을 재현하지 못한다
  같은 상품을 상호금융과 농협은행이 함께 취급할 때 어느 쪽을 담당으로 볼지 정하지 못했다
  정보 최신성 · 중앙 검수 병목 · 계열사 간 담당 충돌 등 운영 리스크가 남는다
```

## 다음

| 한계 | 다음 |
|---|---|
| 효과를 확인하지 못했다 — 조건을 맞추면 Before가 훼손된다 | 안내 노출 후 **재검색률**로 잰다. **실사용 로그에서 비교군을 추린다.** 판정 기준 · 진행 절차 · 자동 기록은 이미 만들어져 있다 |
| 주 KPI에 두 관점이 섞여 있다 | 같은 답이다. **기업 내부 데이터라야 회사 관점의 이탈과 사용자 관점의 성공이 갈린다** |
| K-패스카드 한 사례다 | **0건 로그에서 다음 대상 기능을 고른다.** 같은 방식으로 넓혀지는지 본다 |
| 같은 기능을 여러 채널이 함께 취급할 때 우선순위를 못 정했다 | 노출 개수와 **순서 규칙**을 먼저 합의한다. 채널 목록이 아니라 조직의 문제다 |
| 명부 서명 검증이 없다 | **서명 검증과 키 회전**을 붙인다. 검증 실패 시 안내만 빠지고 검색은 정상 동작하도록 한다 |
| 딥링크 · 화면 컴포넌트가 없다 | **구조상 얹을 수 있게 열어뒀고, 이번엔 만들지 않았다.** 안내의 효과가 미검증인 상태에서 기능을 늘리면 틀린 방향으로 더 멀리 간다. 컴포넌트는 앱 스택과 인터페이스가 달라 전 앱 공통으로 주기 어렵고, 어디서나 줄 수 있는 것은 **데이터 스키마 · 디자인 스펙 · 레퍼런스 구현**까지다 |

## 이 문제가 성립하는 조건

법인이 하나인 회사에서는 덜할 수 있다. 다만 **같은 법인 안에서도 사업부가 나뉘면 생긴다** — 농협은행 안의 NH Pay가 그 예다. 유사한 구조의 다른 기업에서도 같은 문제가 나타나는지는 확인하지 못했다.
