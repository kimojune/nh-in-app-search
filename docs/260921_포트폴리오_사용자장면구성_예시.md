## 01 · 사용자의 순간

### 화면에 넣을 내용

# 카드 이름은 아는데, 어느 앱에서 신청하지?

농협 앱에서 카드 이름으로 검색했다.
콕뱅크는 0건, 스마트뱅킹은 보안카드·OTP 메뉴를 보여줬다.

| NH콕뱅크 | NH스마트뱅킹 |
|---|---|
| 검색어 "케이패스" | 검색어 "경기패스카드" |
| 검색 결과 0건 | 메뉴 15건 · 상품 0건 |

상품을 신청하기 전에, 담당 앱부터 찾아야 했다.

`직접 검색 · 2026.08.18~20`

### 배치·근거 메모

- 제목은 사용 상황을 재구성한 문장이다. 실제 참가자의 인용문처럼 따옴표를 붙이지 않는다.
- 두 앱의 실제 검색 화면을 크게 나란히 배치한다. 캡처의 실제 검색어를 그대로 표시하고, 서로 같은 검색어인 것처럼 편집하지 않는다.
- **본문을 "K-패스카드를 검색했다"에서 "카드 이름으로 검색했다"로 고쳤다(2026-09-23).** 인용한 캡처 둘의 검색어가 서로 다른데 본문이 하나로 적고 있었다. 실측 표에서 두 앱 모두 네 검색어(경기패스카드·카드발급·카드신청·K-패스카드) 전부 같은 결과라 사실은 바뀌지 않는다.
- 스마트뱅킹 칸에 수치를 넣었다(2026-09-23). 메뉴 15건은 전부 보안카드·OTP·카드정보이고 "카드" 두 글자만 매칭된 것이다. 이 칸은 2026-09-21까지 실측 표에 "캡처 누락, 미확인"으로 적혀 있었는데 캡처가 있어 정정했다.
- 자료: `../raw/스크린샷/NH콕뱅크/케이패스검색결과없음.jpg`, `../raw/스크린샷/NH스마트뱅킹/Screenshot_20260818_131248_NH.jpg`.
- 실측 기준: [앱별 검색 결과](./NH앱4개_카드검색_as-is결과.md).

## 02 · 원하던 안내

### 화면에 넣을 내용

# 검색 결과 위에, 담당 앱과 할 일을 먼저 보여준다

**검색어: K-패스카드**

> **K-패스카드 신청은 NH pay에서**
>
> 카드 상품을 확인하고 신청할 수 있어요.
>
> **다음 행동** · NH pay에서 K-패스카드를 찾아보세요.

등록한 저빈도 기능을 검색하면 안내를 상단에 띄운다.
기존 검색 결과는 그 아래에 유지한다.

`안내 문구 예시 · 프로토타입 구현`

### 배치·근거 메모

- 같은 앱의 기존 화면과 개선 화면을 좌우로 보여준다. 개선 화면에는 안내 영역만 강조한다.
- 인용 블록은 이번 구성의 문구 예시다. 현재 구현 화면의 문구와 완전히 같다는 뜻이 아니다. 화면 제작 시 둘을 맞춘다.
- 안내 대상은 등록된 검색어다. 기존 결과가 0건일 때만 뜨는 기능으로 설명하지 않는다.
- 실제 앱 실행 버튼처럼 그리지 않는다. 거래·딥링크는 프로젝트 제외 범위다.
- 근거: `../prototype/router/routing-client.js`의 `lookup()`, `../prototype/router/bank-app.html`의 검색 결과 렌더링.

## 03 · 다음 이용까지

### 화면에 넣을 내용

# 다음번에는 어디서 시작할지 떠올릴 수 있도록

```text
이번에는                 안내를 통해                  다음에는
쓰던 앱에서 검색   →   기능과 담당 앱을 함께 봄   ⇢   담당 앱을 떠올림
```

가끔 쓰는 기능을 찾는 순간마다,
앱별 역할을 자연스럽게 익히게 하려 했다.

`설계 의도 · 이후 기억과 행동 변화는 미검증`

### 배치·근거 메모

- 세 장면을 간단한 흐름으로 표현한다. 마지막 화살표는 점선으로 그려 기대 효과임을 구분한다.
- ‘사용자가 조직도를 외운다’가 아니라 ‘이 기능은 이 앱에서 한다는 관계를 익힌다’는 뜻이다.
- 하나의 카드 안내가 금융그룹 전체의 역할 학습으로 이어진다고 일반화하지 않는다.
- **저빈도와 학습은 서로 당긴다(2026-09-23 추가).** 1년에 한 번 하는 일에서는 "카드는 NH pay"가 외워지지 않는다. 이 장이 성립하는 조건은 저빈도 기능이 하나가 아니라는 것이다. 카드 신청·조합원 배당 조회·통장 재발급은 각각 드물어도 합치면 자주 만난다. 그래서 익히는 것은 개별 대응이 아니라 "모르는 걸 물으면 알려준다"는 쪽에 가깝다. 화면에서 그 구분을 지우지 않는다.

## 04 · 그룹이 보는 문제

### 화면에 넣을 내용

# 사용자는 찾았어도, 그룹은 탐색 접점을 놓칠 수 있다

```text
농협 앱에서 검색   →   찾지 못함   →   외부 검색   →   이후 경로
```

사용자는 밖에서 답을 찾으면 된다.
그룹은 자사 상품을 찾던 고객의 다음 탐색을 외부 검색에 맡긴다.

이 접점의 단절을 그룹 관점의 실패 요소로 보았다.

`사업 관점의 판단 · 거래 손실은 확인하지 않음`

### 배치·근거 메모

- 앱 내부와 외부 검색을 영역으로 나누고, 경계를 넘는 화살표를 강조한다.
- 외부 검색 이후를 무조건 경쟁사 이동·포기로 그리지 않는다. NH로 돌아오는 경로도 가능하다.
- 관찰 근거는 비공식 예비 테스트의 콕뱅크 → 포털 → NH pay 이동이다. 다른 모든 앱에서 같은 이탈이 발생했다고 쓰지 않는다.
- 근거: [과제 수행 기록](./K패스카드_과제수행테스트_진행안.md)의 비공식 예비 테스트.

# K-패스카드 한 기능부터, 안내가 필요한 앱에

| 검색하는 앱 | 확인한 상태 | 안내 적용 방향 |
|---|---|---|
| NH콕뱅크 | 상품명 검색 0건 | 담당 앱과 다음 행동 안내 |
| NH스마트뱅킹 | 카드 상품 대신 관리 메뉴 | 기존 결과 위에 안내 |
| NH올원뱅크 | NH농협카드로 안내 | 기존 안내와 중복 여부 검토 |
| NH pay | 카드 상품 매칭 | 이미 명확한 경로는 중복 안내 억제 |

시범 대상은 담당 정보가 등록된 저빈도 기능으로 제한한다.

`현재 상태는 실측 · 적용 범위는 제안`

### 배치·근거 메모

- 문제 유형과 노출 조건을 구분하는 장이다. ‘0건인 앱 둘’이라고 줄이지 않는다.
- 앱별 참여와 적용 범위가 실제 합의됐다는 뜻은 아니다.
- 첫 화면의 구체적인 장면을 네 앱의 적용 판단으로 넓힌다.
- 근거: [앱별 검색 결과](./NH앱4개_카드검색_as-is결과.md), [MVP 설계](./B축_MVP_설계.md).

## 06 · 서로 다른 도입 이유

### 화면에 넣을 내용

# 그룹에 필요해도, 각 앱이 받아들일 이유는 따로 있다

| 사용자 | 그룹 | 개별 앱 |
|---|---|---|
| 어디서 처리할지 알고 싶다 | 외부 검색으로 끊기는 탐색을 줄이고 싶다 | 상단 공간과 운영 부담을 감수할 실익이 필요하다 |
| 담당 앱과 다음 행동을 본다 | 공통 담당 정보를 제공한다 | 먼저 적용해 보고 참여 범위를 판단한다 |

코드가 짧다는 이유만으로, 도입이 쉽다고 말할 수는 없었다.

`이해관계에 대한 판단 · 실제 참여 의사는 미확인`

### 배치·근거 메모

- 세 열을 동일한 크기로 배치한다. 그룹의 이익만 강조하지 않는다.
- 본문에서 세 주체를 한 번에 비교하는 장은 이 장 하나로 제한한다.
- 근거: [재정비 기록](./포트폴리오_재정비.md)의 도입 비용 주장 철회와 이번 대화의 자율 시범 적용 설명.

## 07 · 도입 방식

### 화면에 넣을 내용

# 각 앱이 먼저 써보고, 실용성이 확인되면 넓힌다

```text
공통 담당 정보 배포  →  참여 앱의 시범 적용  →  사용자 반응·운영 부담 확인  →  확대 판단
       JSON              기능·화면 범위 선택
```

작게 시작할 수 있다.
대신 초기에는 앱마다 안내 범위가 다를 수 있다.

`도입 제안 · 실제 계열사 시범 운영은 미실시`

### 배치·근거 메모

- 이 장에서 처음 JSON을 소개한다. ‘앱이 받아 쓰는 담당 정보 파일’이라는 짧은 설명을 붙여도 된다.
- 공통으로 제공하는 것: 기능, 담당 채널, 역할, 다음 행동 정보.
- 시범 적용에서 앱이 선택하는 것: 참여 여부와 적용 기능·화면 범위. 구체적인 협의·승인 절차는 실제 조직 확인이 필요하다.
- 현재 구현의 중앙 미노출 설정을 앱별 자율 설정 기능으로 오인시키지 않는다. 자율 도입은 도입 제안이고, 현 목업의 모든 기능이 그 운영 체계를 구현한 것은 아니다.
- 중앙회는 공통 기준 관리 주체의 제안으로 설명할 수 있다. 실제 운영 권한이 확인됐다는 표현은 피한다.

# 담당 정보를 등록하고, 앱 화면에 안내가 뜨는 데까지

```text
등록 → 검수·승인 → 발행 → 앱 동기화 → 검색 시 안내
```

| 공통으로 제공 | 앱이 표현 |
|---|---|
| 기능·담당 채널·역할·다음 행동 | 각 앱 디자인에 맞는 안내 화면 |

검색어 조회는 앱 안에서 처리한다.

`프로토타입 구현 · 실제 NH 시스템과 연결되지 않음`

### 배치·근거 메모

- 콘솔 캡처와 안내가 뜬 앱 화면을 나란히 둔다. 구현 구조는 위 흐름 한 줄로 제한한다.
- 콘솔 캡처는 현재 승인·발행 상태가 보이게 새로 촬영해야 한다.
- `../prototype/slides/images/fig-guide-four-designs.png`를 보조 이미지로 사용할 수 있다. 네 앱 비교 이미지는 디자인 비교용이며 실제 앱별 노출 정책을 증명하는 자료는 아니다.
- 근거: [라우터 실행 문서](../prototype/router/README.md).

## 09 · 만들면서 바꾼 정책

### 화면에 넣을 내용

# 발행은 성공했는데, 안내가 나오지 않았다

| 발견한 문제 | 바꾼 정책 |
|---|---|
| 승인된 기준이 없어 빈 정보가 발행됨 | 승인 0건이면 발행을 막고 이유를 알림 |
| 재승인하지 않은 기준이 다음 발행에서 빠짐 | 사라질 기준을 발행 전에 표시 |
| 잘못된 정보가 이미 배포됨 | 이전 내용을 새 버전으로 재발행 |

운영자가 행동하기 전에, 앱에 미칠 영향을 보여주도록 바꿨다.

`구현 중 발견·개선 · 자동 검사 296건 통과 / 2026.09.23 확인`

### 배치·근거 메모

- 검사 수는 작은 보조 근거로 둔다. 핵심은 문제 → 정책 변경이다.
- 이 현상을 최초 발표 실패의 확정 원인이라고 설명하지 않는다. 최초 발표 실패의 원인은 별도 미확인 상태다.
- 근거: [발행 관문과 복구](../prototype/router/README.md), `../prototype/router/tests.mjs`.

## 10 · 확인 범위와 다음 검증

### 화면에 넣을 내용

# 안내는 동작한다. 도움과 학습은 따로 확인해야 한다

| 구분 | 확인 상태 |
|---|---|
| 등록한 정보가 앱 안내로 이어지는가 | 프로토타입에서 확인 |
| 안내를 보고 다음 행동을 이해하는가 | 효과를 판정할 검증은 미완료 |
| 시간이 지나도 담당 앱을 떠올리는가 | 미검증 |
| 각 앱이 운영 부담을 감수할 만큼 유용한가 | 실제 시범 적용 필요 |

**다음 검증**
지금: 안내를 본 뒤, 어디서 무엇을 해야 하는지 설명할 수 있는가?
이후: 안내 없이 같은 기능을 찾을 때, 담당 앱을 떠올리는가?

`검증 상태 · 다음 검증은 제안`

### 배치·근거 메모

- ‘다음 검증’은 이번 예시의 제안이며 이미 수행한 절차가 아니다.
- 과거 As-is는 외부 웹 검색이 가능한 자유 탐색, To-be는 같은 외부 검색 조건을 제공하기 어려운 목업이었다. 두 결과로 단일 개선율을 만들지 않았다는 설명은 부록으로 보낸다.
- 재검색률은 시범 운영의 보조 신호로 사용할 수 있으나, 포기와 해결을 구분하지 못하며 학습을 직접 측정하지 않는다.
- 기존 A01·A02 관찰의 문항·진행 방식·원자료를 확인하기 전에는 성공률로 제시하지 않는다.
- 근거: [평가 리포트](./평가리포트.md), [인수인계 기록](../_meta/HANDOFF.md), 이번 대화의 학습 목표.

## 부록 A · 포털에서 찾으면 되는 것 아닌가?

### 화면에 넣을 내용

# 포털은 실제로 작동하는 대안이었다

| 관찰 사례 | 기록 |
|---|---|
| 비공식 예비 테스트 | 콕뱅크 검색 실패 → 포털 → NH pay, 70초 |
| P01 | 포털 → 삼성카드 공식 웹, 70초 |
| P02 | 포털 → 정책 채널 → 포털 → 신한 웹, 약 4분 30초 |

포털 사용을 사용자 실패로 판정하지 않았다.
그룹 안에서 담당 경로를 안내할 기회가 있다는 관점으로 제안했다.

`조건이 다른 개별 사례 · 합산 성공률을 계산하지 않음`

### 배치·근거 메모

- 근거: [과제 수행 기록](./K패스카드_과제수행테스트_진행안.md).
- P02의 카드사 선택은 주거래 관계로 설명돼 있다. 외부 검색이 경쟁사로 유도했다는 인과 사례로 사용하지 않는다.

## 부록 B · 왜 개선율이 없는가?

### 화면에 넣을 내용

# 기존 테스트와 개선안의 탐색 조건이 달랐다

| 기존 환경 · As-is | 개선안 · To-be |
|---|---|
| 실제 앱과 외부 웹 검색을 자유롭게 사용 | 프로토타입에서 같은 외부 검색 조건을 제공하기 어려움 |

조건이 다른 결과를 하나의 개선율로 계산하지 않았다.
안내 이해와 이후 기억은 별도의 질문으로 확인하려 한다.

`당시 검증의 한계 · 후속 검증 제안`

### 배치·근거 메모

- 모든 사용자 테스트가 불가능하다는 의미로 쓰지 않는다. 당시 목업과 테스트 조건의 제한을 설명한다.
- 근거: [평가 리포트](./평가리포트.md)와 이번 대화에서 확인한 당시 제약.

## 부록 C · 각 앱이 왜 도입하겠는가?

### 화면에 넣을 내용

# 그룹의 필요만으로 앱의 참여가 보장되지는 않는다

| 각 앱이 부담하는 것 | 시범 적용에서 확인할 것 |
|---|---|
| 검색 결과 상단 공간 | 안내가 사용자에게 실제로 도움이 되는가 |
| 앱별 화면 적용 | 제한된 기능부터 적용 가능한가 |
| 정보 검토·갱신 업무 | 담당자와 유지 가능한 절차가 있는가 |

기술적으로 배포할 수 있다는 것과,
각 법인이 받아들일 이유가 있다는 것을 구분했다.

`도입 판단의 기준 · 참여 의사와 운영 비용은 미확인`

### 배치·근거 메모

- 실제 계열사 인터뷰나 합의 결과로 제시하지 않는다.
- 후속 정책 후보: 복수 채널 정렬, 정보 갱신 책임, 안내 긴급 중단, 확대 판단 기준.
- 근거: [재정비 기록](./포트폴리오_재정비.md), [MVP 설계의 운영 한계](./B축_MVP_설계.md), 이번 대화의 도입 구상.
