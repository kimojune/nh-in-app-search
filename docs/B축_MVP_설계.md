# 검색·담당 채널 안내 프로토타입 설계

- 최종 수정일: 2026-08-24
- 문서 유형: 종료 시점 스냅샷 — 2026-08-28 프로젝트 종료 이후 갱신하지 않는다
- 목적: 금융사가 기존 검색에 적용할 수 있는 저빈도 금융 기능 담당 채널 안내 방식을 프로토타입으로 명세한다.
- 첫 적용 사례: NH 앱 4개에서 K-패스카드 담당 채널을 찾는 상황

> 파일명에는 과거 분류인 `B축`이 남아 있지만, 현재는 자유 탐색 Before와 안내형 After를 하나의 검증 흐름으로 본다. 이 프로토타입은 실제 NH 앱이나 백엔드를 구현하는 작업이 아니다.

> **2026-08-24 갱신**: 이 문서가 명세한 구조를 실제로 동작하는 구현으로 만들었다 — [`prototype/router/`](../prototype/router/README.md). 아래 내용 중 "구현하지 않는다"고 적힌 항목의 현재 상태는 각 절에 표시했다. 결정 경위는 [`decision-log/라우터_실동작구현.md`](./decision-log/라우터_실동작구현.md).

## 해결안 요약

```text
사용자 검색어
  → 승인된 기능·카테고리 매핑
  → 처리 가능한 담당 채널 목록
  → 채널별 역할 표시: [완료]·[경유]·[안내]
  → 사용자가 적절한 채널과 다음 행동을 결정
```

정확한 상품 화면으로 자동 이동시키는 것이 아니라, 사용자가 **어디에서 무엇을 할 수 있는지** 판단할 수 있게 한다. 검색 결과가 없을 때뿐 아니라 결과가 있어도 담당 채널이나 다음 행동이 불명확할 때 안내를 노출한다.

## 왜 이 범위인가

- 저빈도 기능은 사용자가 기능명은 알아도 어느 앱·메뉴가 담당하는지 기억하기 어렵다.
- NH는 슈퍼앱 통합을 추진하고 있지만 상호금융·지역농협·농협은행·카드 등 운영 주체가 다르다.
- 모든 기능과 데이터를 한 앱에 통합하면 개발·운영 복잡도와 화면 과밀 문제가 커질 수 있다.
- 따라서 기존 검색 위에 얹을 수 있는 최소 기능인 `검색어–기능–담당 채널` 안내를 제안한다.

실제 도입 비용이 낮다고 확정한 것은 아니다. 이 프로젝트에서는 거래 연동, 개인화, 실시간 상품 데이터 통합을 제외해 **전체 기능 통합안보다 구현 범위를 작게 잡았다**는 수준까지만 주장한다.

## 핵심 데이터 구조

| 필드 | 예시 | 설명 |
|---|---|---|
| 사용자 표현 | `K-패스`, `케이패스`, `교통비 환급 카드` | 검색어·동의어 |
| 기능·카테고리 | `교통비 환급 카드 신청` | 사용자가 하려는 일 |
| 담당 채널 | `NHPAY`, `모바일웹`, `올원뱅크` | 처리 또는 안내 가능한 접점 |
| 채널 역할 | `완료`, `경유`, `안내` | 해당 채널에서 할 수 있는 수준 |
| 다음 행동 | `카드 검색 후 신청`, `담당 채널 확인` | 자동 이동이 아닌 행동 지침 |
| 상태 | `등록`, `검토 중`, `승인`, `반려` | 운영·배포 상태 |

## 복수 담당 채널 정책

한 기능을 여러 채널에서 다룰 수 있으므로 하나의 ‘정답 앱’으로 단정하지 않는다.

- `완료`: 해당 채널에서 조회·신청 등 사용자의 목적을 끝낼 수 있다.
- `경유`: 관련 화면까지 안내하거나 다른 채널로 연결하지만 그 안에서 완료되지는 않는다.
- `안내`: 담당 채널과 다음 행동에 대한 정보만 제공한다.

가능한 채널을 함께 보여주되 각 역할을 명시한다. 채널 수가 많을 때의 노출 개수, 정렬 우선순위, 개인별 추천은 아직 확정하지 않는다.

## 노출 조건

다음 중 하나면 안내 컴포넌트를 노출한다.

1. 검색 결과가 0건이다.
2. 관련 결과는 있으나 담당 채널이 드러나지 않는다.
3. 결과를 눌러도 사용자가 다음 행동을 판단하기 어렵다.

현재 채널에서 정확한 처리 경로와 다음 행동이 이미 명확하면 중복 안내를 노출하지 않는다.

## 사용자 화면 예시

> **K-패스카드는 다음 채널에서 처리할 수 있어요**
>
> - **NHPAY · 완료** — 카드 상품을 확인하고 신청할 수 있어요.
> - **모바일웹 · 완료** — 앱 설치 없이 상품을 확인하고 신청할 수 있어요.
> - **올원뱅크 · 안내** — 담당 채널 정보를 확인할 수 있어요.

프로토타입에서 채널 선택은 사용자의 판단을 관찰하기 위한 선택이며, 실제 앱 실행·딥링크·신청 거래는 구현하지 않는다.

## 검증 기준

아래 지표들은 **아직 하나도 측정되지 않았다.** 안내형 After 테스트가 있어야 나오는 값이고, 그 테스트는 2026-08-24에 이번 마감 범위에서 제외하기로 결정했다. **문구는 확정된 그대로 두고 상태만 표시한다.**

지금까지 실제로 측정된 것은 아래 「지금까지 측정된 것」 절에 따로 모았다. **두 묶음을 섞어 제시하지 않는다** — 아래쪽은 문제의 크기와 도입 가능성을 말하지, 안내의 효과를 말하지 않는다.

### 1차 KPI — 검증 예정

`외부 재검색이나 진행자 도움 없이 인앱검색만으로 올바른 담당 채널과 다음 행동을 결정한 참가자 비율`

**미측정.** 진행 절차와 판정 기준은 [`사용성테스트_B축프로토타입_진행안.md`](./사용성테스트_B축프로토타입_진행안.md)에 준비돼 있고, 남은 것은 참가자 모집이다.

### 보조 지표 — 검증 예정

- 올바른 채널 선택률
- 올바른 다음 행동 설명률
- 결정까지 걸린 시간
- 검색어 재입력 횟수
- 외부 검색·도움 요청 비율
- 채널 역할 오해율

### 가드레일 — 하나는 Before 값이 있다

- **잘못된 채널을 확신하는 비율** — 인식 설문 25건에서 근사치가 나왔다. 앱을 먼저 여는 15명 중 **7명이 담당 앱이 아닌 것을 고르고도 확신도 4~5를 줬다.** 자기보고이고 5지선다라는 한계가 있지만, 이 층에서 유일한 실측 근사치다. After 값과 비교할 Before로 쓸 수 있다
- 안내를 실제 자동 이동 또는 신청 완료로 오해하는 비율 — 미측정
- 복수 채널 제시로 결정을 못 하는 비율 — 미측정

## 운영 단계 지표 — 배포 후에 재는 것

위 검증 기준은 **통제된 사용성 테스트용**이다. 참가자에게 과제와 보기를 주고 재므로, 실제 사용자가 아무 검색어나 치고 아무 앱이나 열고 언제든 나가버리는 상황과 다르다. **선택지를 주는 순간 회상이 재인으로 바뀌어 성공률이 실제보다 높게 나온다.** 이 한계는 방법 자체에서 오는 것이라 없앨 수 없고 밝혀야 한다.

그래서 배포 후에 쓸 지표를 따로 둔다. **전부 각 계열사 앱이 자기 로그만으로 잰다.** 이 설계는 검색당 네트워크가 0이고 검색어를 밖으로 보내지 않으므로 라우터는 사용자 행동을 관측하지 못한다. 측정 주체가 계열사인 것이 원칙과 맞다.

### 주지표 — 안내 노출 후 재검색률

```text
정의   안내가 노출된 검색 세션 중, 같은 세션 안에서 검색어를 다시 입력한 세션의 비율
계산   재검색 발생 세션 ÷ 안내 노출 세션
```

**안내가 답이 됐으면 다시 치지 않는다.** 사용자가 원하는 것을 얻었는지를 가장 가깝게 대신 말해주는 신호다.

**조작에 강하다.** 카드를 키우거나 문구를 자극적으로 만들어도 재검색은 줄지 않는다. 오히려 헛되이 눌리면 늘어난다. 클릭률과 반대 방향이라 굿하트의 법칙에 덜 걸린다.

**놓치는 것** — 다시 치지 않았지만 그냥 포기한 경우를 성공으로 센다. 그래서 단독으로 쓰지 않고 아래 보조와 함께 본다.

**비교군을 어떻게 만드나.** 안내가 뜨는 검색어와 안 뜨는 검색어는 애초에 다르므로 그냥 비교하면 편향된다. 두 가지로 푼다.

```text
단계적 배포    앱마다 스냅샷을 받는 시점을 달리한다
               먼저 받은 앱과 아직 안 받은 앱을 비교 → 자연 비교군
같은 검색어군   안내 노출 전후 같은 검색어의 재검색률을 비교
```

단계적 배포는 이 구조에 이미 들어 있다. 앱마다 동기화 시점이 다르고 `suppressIn`으로 앱별 노출을 끌 수 있다. **실험 도구를 새로 만들 필요가 없다.**

### 보조 1 — 안내 없는 0건 비율

```text
정의   결과가 0건이면서 안내도 붙지 않은 검색의 비율
계산   안내 없는 0건 ÷ 전체 0건
```

**제로결과율(ZRR)을 그대로 쓰지 않는 이유가 여기 있다.** 라우터가 담당 채널을 책임지면 각 앱은 자기 담당이 아닌 것에 억지로 답할 이유가 없어진다. 무관한 결과를 걷어내면 **0건이 오히려 늘어나는데 그게 개선이다.** ZRR을 내려야 할 값으로 두면 **쓸모없는 결과를 남길 유인**이 생긴다.

그래서 0건을 둘로 가른다.

```text
안내가 붙은 0건    정상 처리다. 이 기능이 하려는 일이다
안내가 없는 0건    아직 등록되지 않은 표현이다. 이것만 줄인다
```

이 구분은 콘솔의 `로그로 후보 찾기`가 이미 하고 있는 일과 같다. 그 화면이 0건 쿼리를 `미등록`·`이미 등록됨`·`등록됨·미승인`으로 가른다.

### 보조 2 — 검색당 결과 수와 무관 결과 정리

라우터가 담당 채널을 맡으면 **각 앱이 자기 인덱스를 정리할 수 있게 된다.** 지금은 올원뱅크에서 `카드신청`을 치면 39건이 나오는데 전부 퇴직연금 관련이다. 자기 담당이 아닌 것을 억지로 매칭해 보여주는 결과다.

**이것은 라우터가 하는 일이 아니라, 라우터가 있으면 각 앱이 할 수 있게 되는 일이다.** 이 도구는 검색 자체를 고치지 않는다는 원칙은 그대로다.

```text
검색당 결과 수(중앙값)   정리 전후를 비교한다. 짧고 정확해져야 한다
결과 무클릭 비율        결과가 나왔는데 아무것도 누르지 않고 재검색하거나 나간 비율
                       결과가 있어도 쓸모없었다는 신호다. ZRR이 못 잡는 실패를 잡는다
```

as-is의 진짜 문제가 0건이 아니라 이쪽이다. **결과가 39건 있는데 전부 무관한 상태**를 ZRR은 성공으로 센다.

### 보조 3 — 그 밖에

```text
안내 카드 채널 탭률     관심의 신호이지 성공이 아니다. 주지표로 쓰지 않는다
                       탭률이 오르는데 재검색률이 안 내려가면 경고로 읽는다
같은 검색어 반복        같은 사용자가 며칠에 걸쳐 같은 말을 다시 치면 끝내 해결하지 못한 것이다
                       세션 안 재검색이 놓치는 실패를 잡는다
고객센터 문의 건수      "어디서 신청하나요" 류 문의가 줄면 그것이 곧 효과다
                       금융사가 이미 재고 있고 비용으로 환산되는 값이다
                       다만 문의 분류 체계가 필요하고 다른 요인에 흔들린다
```

### 주지표로 쓰지 않기로 한 것

- **제로결과율(ZRR) 단독** — 위 보조 1의 이유. 내려야 할 값으로 두면 쓸모없는 결과를 남길 유인이 생긴다.
- **안내 카드 클릭률(CTR)** — 카드를 키우고 문구를 자극적으로 만들면 오른다.
- **그룹 안 이동률** — 안내가 지목한 계열사 채널이 실제로 열렸는지를 재는 값이다. 세 가지 이유로 쓰지 않는다. **(1)** 계열사끼리 사용자를 식별해 맞춰야 하므로 `앱은 조회만, 검색어는 밖으로 보내지 않는다`는 성립 조건을 깬다. **(2)** 측정하려고 도입 장벽을 도로 올린다. **(3)** 그룹 안으로 보낼수록 오르는 값이라, 사용자에게 그룹 밖이 더 나은 경우에도 지표는 좋아진다.

### 함께 읽는 법

```text
안내 없는 0건은 내려가는데 재검색률이 안 내려간다
  → 검색어는 걸리는데 안내 내용이 도움이 안 된다. 안내 문구와 채널 구성을 고친다

재검색률은 내려가는데 안내 없는 0건이 그대로다
  → 이미 등록된 표현에서는 잘 되지만 새 표현을 못 따라가고 있다. 로그 수집 주기를 줄인다

탭률만 오르고 재검색률이 그대로다
  → 눈에 띄기만 하고 답이 되지 못하고 있다
```

### 전부에 걸리는 한계

- **실제 배포 후에만 잰다.** 지금은 실사용 로그가 없어 하나도 측정할 수 없다. 여기 적은 것은 `배포하면 이렇게 재겠다`는 설계다.
- **앱을 벗어난 뒤는 보지 못한다.** 포털로 갔는지, 다른 앱을 열었는지 알 수 없다. 그것이 검색어를 밖으로 보내지 않는 대가다.
- **자연 비교군은 무작위 배정이 아니다.** 단계적 배포로 만드는 비교군은 앱과 사용자층이 다르므로, 차이를 안내 하나로 돌리려면 검색어군을 맞춰 보정해야 한다.

## 한계

- NH의 실제 검색 인덱스, 조직 권한, 운영 비용을 확인하지 못했다.

- 웹 프로토타입은 실제 앱 전환, 로그인, 설치, 신청 과정의 마찰을 재현하지 못한다.
