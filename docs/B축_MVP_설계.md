# 검색·담당 채널 안내 프로토타입 설계

- 최종 수정일: 2026-08-22
- 문서 유형: 계속 갱신
- 목적: 금융사가 기존 검색에 적용할 수 있는 저빈도 금융 기능 담당 채널 안내 방식을 프로토타입으로 명세한다.
- 첫 적용 사례: NH 앱 4개에서 K-패스카드 담당 채널을 찾는 상황

> 파일명에는 과거 분류인 `B축`이 남아 있지만, 현재는 자유 탐색 Before와 안내형 After를 하나의 검증 흐름으로 본다. 이 프로토타입은 실제 NH 앱이나 백엔드를 구현하는 작업이 아니다.

## 해결안 요약

```text
사용자 검색어
  → 승인된 기능·카테고리 매핑
  → 처리 가능한 담당 채널 목록
  → 채널별 역할 표시: [완료]·[경유]·[안내]
  → 사용자가 적절한 채널과 다음 행동을 결정
```

정확한 상품 화면으로 자동 이동시키는 것이 아니라, 사용자가 **어디에서 무엇을 할 수 있는지** 판단할 수 있게 한다. 검색 결과가 없을 때뿐 아니라 결과가 있어도 담당 채널이나 다음 행동이 불명확할 때 안내를 노출한다.

## 왜 이 범위인가

- 저빈도 기능은 사용자가 기능명은 알아도 어느 앱·메뉴가 담당하는지 기억하기 어렵다.
- NH는 슈퍼앱 통합을 추진하고 있지만 상호금융·지역농협·농협은행·카드 등 운영 주체가 다르다.
- 모든 기능과 데이터를 한 앱에 통합하면 개발·운영 복잡도와 화면 과밀 문제가 커질 수 있다.
- 따라서 기존 검색 위에 얹을 수 있는 최소 기능인 `검색어–기능–담당 채널` 안내를 제안한다.

실제 도입 비용이 낮다고 확정한 것은 아니다. 이 프로젝트에서는 거래 연동, 개인화, 실시간 상품 데이터 통합을 제외해 **전체 기능 통합안보다 구현 범위를 작게 잡았다**는 수준까지만 주장한다.

## 핵심 데이터 구조

| 필드 | 예시 | 설명 |
|---|---|---|
| 사용자 표현 | `K-패스`, `케이패스`, `교통비 환급 카드` | 검색어·동의어 |
| 기능·카테고리 | `교통비 환급 카드 신청` | 사용자가 하려는 일 |
| 담당 채널 | `NHPAY`, `모바일웹`, `올원뱅크` | 처리 또는 안내 가능한 접점 |
| 채널 역할 | `완료`, `경유`, `안내` | 해당 채널에서 할 수 있는 수준 |
| 다음 행동 | `카드 검색 후 신청`, `담당 채널 확인` | 자동 이동이 아닌 행동 지침 |
| 상태 | `등록`, `검토 중`, `승인`, `반려` | 운영·배포 상태 |

## 복수 담당 채널 정책

한 기능을 여러 채널에서 다룰 수 있으므로 하나의 ‘정답 앱’으로 단정하지 않는다.

- `완료`: 해당 채널에서 조회·신청 등 사용자의 목적을 끝낼 수 있다.
- `경유`: 관련 화면까지 안내하거나 다른 채널로 연결하지만 그 안에서 완료되지는 않는다.
- `안내`: 담당 채널과 다음 행동에 대한 정보만 제공한다.

가능한 채널을 함께 보여주되 각 역할을 명시한다. 채널 수가 많을 때의 노출 개수, 정렬 우선순위, 개인별 추천은 아직 확정하지 않는다.

## 노출 조건

다음 중 하나면 안내 컴포넌트를 노출한다.

1. 검색 결과가 0건이다.
2. 관련 결과는 있으나 담당 채널이 드러나지 않는다.
3. 결과를 눌러도 사용자가 다음 행동을 판단하기 어렵다.

현재 채널에서 정확한 처리 경로와 다음 행동이 이미 명확하면 중복 안내를 노출하지 않는다.

## 사용자 화면 예시

> **K-패스카드는 다음 채널에서 처리할 수 있어요**
>
> - **NHPAY · 완료** — 카드 상품을 확인하고 신청할 수 있어요.
> - **모바일웹 · 완료** — 앱 설치 없이 상품을 확인하고 신청할 수 있어요.
> - **올원뱅크 · 안내** — 담당 채널 정보를 확인할 수 있어요.

프로토타입에서 채널 선택은 사용자의 판단을 관찰하기 위한 선택이며, 실제 앱 실행·딥링크·신청 거래는 구현하지 않는다.

## NH 앱 4개 적용 예시

| 앱 | 관찰된 상태 | 안내형 적용 예시 |
|---|---|---|
| NHPAY | K-패스카드 검색이 비교적 정확함 | 기존 결과 유지, 불필요한 결과만 정리 |
| NH콕뱅크 | 관련 검색어는 실패하거나 일반 카드 목록으로 이동 | 동의어 매핑 후 처리 채널과 역할 안내 |
| NH올원뱅크 | 관련 메뉴는 있으나 K-패스카드 처리 경로가 불명확 | 기존 결과와 함께 담당 채널 안내 |
| NH스마트뱅킹 | 카드 상품 인덱스·신청 메뉴가 확인되지 않음 | 0건 화면에서 가능한 처리 채널 안내 |

세부 관찰 근거는 [`NH앱4개_카드검색_as-is결과.md`](./NH앱4개_카드검색_as-is결과.md)에 둔다. 앱별 화면 차이는 사례 설명용이며, 해결안의 일반화 단위는 ‘저빈도 금융 기능’이다.

## 등록·승인·배포 흐름

```text
계열사·담당 부서가 매핑 등록
  → 중앙 관리자가 표현·기능·채널 역할 검토
  → 승인
  → 검색 안내에 배포
```

- 등록 책임: 해당 기능을 운영하는 계열사 또는 담당 부서
- 승인 책임: 중앙 검색 정책 관리자
- 배포 조건: 승인 완료
- 수정·폐기 이력, 검토 SLA, 책임 충돌 해결 방식은 실제 조직 확인 전까지 미정

프로토타입에서는 이 흐름을 최소 화면으로만 재현하며 실제 관리자 권한·데이터 동기화는 구현하지 않는다.

## 구현 화면

- [ ] 사용자 검색 화면: 자유 검색어 입력
- [ ] 검색 결과 화면: 기능명, 복수 채널, 역할, 다음 행동 표시
- [ ] 0건 또는 불명확 결과 안내 상태
- [ ] 등록 화면: 표현·기능·채널·역할 입력
- [ ] 관리자 검토 화면: 승인·반려
- [ ] 승인 후 사용자 검색 결과에 반영되는 상태

## 검증 기준

### 1차 KPI

`외부 재검색이나 진행자 도움 없이 올바른 담당 채널과 다음 행동을 결정한 참가자 비율`

### 보조 지표

- 올바른 채널 선택률
- 올바른 다음 행동 설명률
- 결정까지 걸린 시간
- 검색어 재입력 횟수
- 외부 검색·도움 요청 비율
- 채널 역할 오해율

### 가드레일

- 잘못된 채널을 확신하는 비율
- 안내를 실제 자동 이동 또는 신청 완료로 오해하는 비율
- 복수 채널 제시로 결정을 못 하는 비율

자유 탐색 Before와 안내형 프로토타입 After는 환경과 과제가 다르므로 동일 조건 실험처럼 `0% → 100%`, `47초 → 즉시`의 직접 개선값을 만들지 않는다. 신청 전환율은 담당 채널 결정이 개선되면 따라올 수 있는 후행 가설이며 이번 프로토타입의 직접 KPI가 아니다.

## 현재 결과물과의 관계

기존 [`prototype/b축_사용성테스트_프로토타입.html`](../prototype/b축_사용성테스트_프로토타입.html)과 과거 ThinkCode 프롬프트는 ‘공통 목적지 자동 이동’ 전제를 담고 있다. 이는 현재 해결안의 검증물로 사용하지 않고, 안내형 프로토타입으로 수정한 뒤 After 테스트를 진행한다. 기존 결과는 의사결정 변화의 기록으로만 보존한다.

## 한계

- NH의 실제 검색 인덱스, 조직 권한, 운영 비용을 확인하지 못했다.
- K-패스카드 한 사례만으로 모든 저빈도 금융 기능에 일반화할 수 없다.
- 복수 채널의 정렬·우선순위와 정보 최신성 관리 비용은 검증 전이다.
- 외부 검색 이탈이 항상 나쁜 것은 아니다. 공식 정보 확인 등 필요한 탐색과 불필요한 재검색을 구분해야 한다.
- 웹 프로토타입은 실제 앱 전환, 로그인, 설치, 신청 과정의 마찰을 재현하지 못한다.
